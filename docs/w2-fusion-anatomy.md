# W2 预备：把融合这一步拆开看

**状态**：探索性，**未预注册**，不定任何胜负。

W1 留下的最扎眼的一条是 A→B **−5.43pp**：往内容面上加两个词面索引，结果变差。词面
可解性审计（`docs/query-set-lexical-audit.md`）把病因往前推了一步——词面面**有**东西

三条声明，写在前面，因为后面每一节都受它约束：

  **关于算子的陈述**，不是关于这个库的陈述。
- 除第 1 节那个 bug 修复之外，**没有改动任何默认行为**。新增的档位全部在 `EXPLORATORY`
  里，默认关闭，不进预注册的 A–E 阶梯。

原始数据：`eval/lex-facet-split.json`、`eval/fusion-arith.json`。脚本：

## 1 先修 bug：`lex_tri` 在中文查询上从来没工作过

这不是本页要找的东西，是拆 Facet 3 的时候撞上的。它跟结论无关地存在了很久，所以先说。

### 1.1 缺陷

`build_fts_query(query, segmented=False)` 是喂给 trigram 索引的那一路。它原来只做一件
事：按**空白**切词，每片加引号，丢掉长度小于 3 的片。

对英文这是对的。对中文这是灾难：**中文句子没有空格**，所以整句话作为一个"词"到达，
被整体加上引号，变成一个 12 字的**短语查询**。也就是说，`lex_tri` 在中文查询上问索引的
是"哪一页逐字包含用户写的整句话"。

真实页面不会逐字包含用户的整句话。这个子句是**保证落空**的。

### 1.2 测量（479 条 W1 查询，`library-w1-indexed.db`）

| | n | 修复前 `lex_tri` 非空 | 修复后 `lex_tri` 非空 |
|---|---|---|---|
| 中文查询 | 211 | **25（11.85%）** | **202（95.73%）** |
| 拉丁查询 | 268 | 268（100%） | 268（100%） |

修复前 `lex_tri` 返回空的 **186 条全部是中文，拉丁一条都没有**。换句话说：**这个面存在
的全部理由就是"unicode61 切不开无空格的中文"这个盲区，而它恰恰在 88% 的中文查询上
是缺席的**。

复现代码留在 `scripts/lex_facet_split.py` 的 `trigram_coverage()` 里——旧表达式在那里被
**重建**而不是被描述，这样缺陷在造成它的代码删掉之后仍然可以从仓库里复算。

### 1.3 修复

含中日韩字符的片切成**重叠 3-gram**；拉丁片保持整词不动（引号里的 `compar` 经同一个
分词器已经能匹配 `comparison`，把词切碎只会加噪声）。三元组这一路加了
`TRI_MAX_TERMS = 48` 的截断，防止一段长文本炸出几百个 OR 子句。

```
如何查看浏览器历史记录   ->  "如何查" OR "何查看" OR "查看浏" OR ... OR "史记录"   （9 个）
sqlite-vec 向量检索      ->  "sqlite" OR "vec" OR "向量检" OR "量检索"
机器学习 论文            ->  "机器学" OR "器学习"          （"论文"两字不足 3，正确丢弃）
工具                     ->  None                          （仍然正确：无可匹配的三元组）
```

五项新测试把行为钉死：CJK 句子变成重叠三元组、**三元组真的能匹配到文档**（不是只检查
字符串形状）、拉丁词不被切碎、扩展被 48 截断、中英混排时拉丁保持整词而中文被切。

### 1.4 为什么 840 项测试没有发现它

因为**没有一项测试、没有一个评测数字曾经看过 `lex_tri` 单独的输出**。它一直和 `lex_seg`
一起被 RRF 融合成 Facet 3 的一个结果，而 `lex_seg` 在中文上是工作的，于是融合结果始终
"看起来正常"。模块 docstring 里那张论证两个索引都必要的表，用的 ground truth 是
`工具` / `论文` / `提示词` / `效率工具` 这种 2–4 字**查词**——短查词恰好没有空白切分
问题，所以那张表是对的，同时也完全测不到这个缺陷。

**教训不是"要多写测试"，是"融合掩盖了成员的失效"**——这恰好也是本页第 3、4 节的主题。

### 1.5 修好之后质量没有变

同一个词面可解性脚本在修好的代码上原样重跑（`docs/query-set-lexical-audit.md` §4）：
整体 R@5 **0.4802 → 0.4802，+0.00pp**。`q_vague` +0.74pp，`q_episodic` −0.58pp，
`q_content` 不动。

**修 bug 是对的，把它记成质量改进是不诚实的。** 两句话都要写在变更记录里。

## 2 拆开 Facet 3：两个索引各值多少

`facetmark.text` 论证过为什么要维护两张 FTS5 表，但那是在一个标定库上用 2–4 字查词做
ground truth 论证的。此后两个索引一直作为一个块被融合，**没有任何一半单独对着真实查询
打过分**。

三个档位，都不含向量，因此都不需要模型：

| 档位 | 组成 |
|---|---|
| `seg_only` | `lex_seg`（jieba + unicode61） |
| `tri_only` | `lex_tri`（trigram） |
| `lex_only` | 两个 RRF 融合——**这就是 B/C/D 里 Facet 3 的实际形态** |

### 2.1 结果（R@5，n=479，修复后）

| 分组 | n | `seg_only` | `tri_only` | `lex_only`（融合） | 融合 − seg | CI95 | 赢/输 | p |
|---|---|---|---|---|---|---|---|---|
| 全部 | 479 | 0.4843 | 0.4572 | 0.4802 | **−0.42pp** | [−2.09, +1.25] | 8 / 10 | 0.815 |
| 中文 | 211 | 0.2607 | 0.2464 | 0.2701 | +0.95pp | [−1.90, +3.79] | 6 / 4 | 0.754 |
| 拉丁 | 268 | 0.6604 | 0.6231 | 0.6455 | −1.49pp | [−3.73, +0.37] | 2 / 6 | 0.289 |
| `q_content` | 171 | 0.7953 | 0.7602 | 0.8012 | +0.58pp | [−2.34, +3.51] | 4 / 3 | 1.000 |
| `q_vague` | 136 | 0.4779 | 0.4559 | 0.4706 | −0.74pp | [−4.41, +2.94] | 3 / 4 | 1.000 |
| `q_episodic` | 172 | 0.1802 | 0.1570 | 0.1686 | −1.16pp | [−3.49, +1.16] | 1 / 3 | 0.625 |

配对法与 `scripts/intent_strata.py` 一致：精确双侧 McNemar + 配对 percentile bootstrap
（10,000 次重采样，种子 20260803）。

反方向的对照：`tri_only → lex_only` 全部 **+2.30pp**，CI95 [+0.42, +4.18]，16 赢 5 输，
p = 0.027。也就是说，**融合确实救了 `tri_only`，但没救到 `seg_only` 的水平**。

### 2.2 措辞纪律

**正确说法**：在这批查询上，把 `lex_tri` 加到 `lex_seg` 上的效果**与零不可区分**——所有
六个分组的置信区间都包含 0。

**不能说**："`lex_tri` 更差""应该删掉 `lex_tri`"。理由有三条：

1. 置信区间宽到 ±2pp，这批查询的功效不足以分辨 ±1pp 的效应；
2. 下面 2.3 的 13 条独有命中是真的；
3. 这批查询本身就是产生这个假设的那批，按 §9 的规矩它只能描述，不能判定。

### 2.3 互补性：两个索引确实互补，融合确实漏接

seg / tri 四格表（k = 5，全部 479 条）：

| | `seg_only` 命中 | `seg_only` 未命中 |
|---|---|---|
| `tri_only` 命中 | 206 | **13** |
| `tri_only` 未命中 | 26 | 234 |

**13 条只有 trigram 能解**（2.71%），互补性不是零。但**融合只保住了其中 8 条**——另外
5 条在被 `lex_seg` 的排序稀释后掉出前五。中文分组里是 8 条独有、保住 6 条；拉丁 5 条
独有、保住 2 条。

这是同一个病在一层更小的尺度上重演：**一个面独有的强命中，穿不过 RRF**。这正是下面
两节要量的东西。

## 3 RRF 的算术：加性打分给不出"单面保护"

这一节**完全不依赖数据**。给定出厂常数 `rrf_k = 60`、`candidates_per_facet = 50`、
权重 content / intent / lex_seg = 1.0、lex_tri = 0.7，下面每个数都是算出来的。

### 3.1 一个面能给出的最高分是多少

一个只被单个面认识、且被那个面排在**第一**的文档，得分上限是

```
1.0 / (60 + 1) = 0.016393
```

### 3.2 "每个面都排在最后一名"能拿多少

一个被**所有面都排在候选深度最末（第 50 名）**的文档——即每个面都认为它勉强够格、
谁都不看好——得分是各面之和：

| 档位 | 面 | 总权重 | 全面垫底得分 | 与单面第一之比 |
|---|---|---|---|---|
| B | content + lex_seg + lex_tri | 2.7 | 0.024545 | **1.50×** |
| C / D | content + intent + lex_seg + lex_tri | 3.7 | 0.033636 | **2.05×** |

**两个档位都能压过单面第一名。** 在 C/D 里，"四个面一致认为你排第 50"比"一个面认为你
排第 1"值两倍还多。

### 3.3 交叉排名：这不是边缘情形，是常态

真正说明问题的是交叉点。两个 1.0 权重的面共同持有的文档，只要它在两个面里的排名好于

```
2.0 × (60 + 1) / 1.0 − 60 = 62
```

就赢过单面第一名。而**候选深度只有 50**——第 62 名根本不在候选池里。也就是说，
**任何被两个满权重面同时召回的文档，都必然赢过任何单面第一名**，无一例外。

按档位算交叉点：B 档 **104.7**，C/D 档 **165.7**，都远在深度 50 之外。

这就是 A→B 那 −5.43pp 的机械解释的候选之一：加进 Facet 3 不只是"加了一个弱面"，是
**给了每一个被词面粗略召回的文档一张选票，而这些票的总和结构性地压过了任何单面确信**。

### 3.4 要修需要多少代价

一个自然的补丁是加一个 CombMAX 项，即

```
score = Σ_f  w_f / (k + r_f)   +   λ · max_f  w_f / (k + r_f)
```

要恢复"某个面排第一的文档不应该输给所有面都垫底的文档"这条**最弱的保证**，需要

| 档位 | 所需 λ |
|---|---|
| B | **≥ 1.116** |
| C | **≥ 2.361** |

λ > 1 意味着 max 项必须**压过整个 sum 项**。换句话说：想在 RRF 里保住单面确信，代价是
让融合基本退化成"取最好的那个面"。**这本身就是一条结论——纯加性的打分融合给不出单面
保护，这不是参数没调好。**

（λ 的这两个数是"恢复保证所需的下界"，不是推荐值。任何真要上线的 λ 必须在新查询集上
定，见第 5 节。）

## 4 在真实查询上，掩埋确实发生

算术说"可能发生"，这一节数"发生了多少"。两个词面面不需要向量，所以 479 条查询可以
原样重放（`scripts/fusion_arith.py`）。**两个面是最温和的情形**——出厂的 C 和 D 融四个
面——所以下面每个数字都是**下界**。

（本节必须在三元组修复之后跑。修复前 `lex_tri` 对 186 条查询返回空，39% 的查询根本
到不了融合这一步，掩埋统计会落在一个偏拉丁的残余样本上。）

### 4.1 单面第一名的下场

470 条查询真正进入融合（余下 9 条只有 `lex_seg` 非空——每一片都短于 3 字，trigram 索引
无从匹配，这是合法情形）。其中 **205 条两个面对"第一名是谁"意见不一致**。

一共出现 **102 个"只有一个面认识、且被那个面排第一"的文档**：

| | 数量 | 占比 |
|---|---|---|
| 融合后中位名次 | **15** | — |
| 掉出前 10 | 66 | 64.7% |
| 掉出前 5 | **81** | **79.4%** |

按查询类型（sole / 掉出前 5）：`q_content` 29 / 18、`q_vague` 30 / 24、
`q_episodic` 43 / 39。

这个比例不是巧合，第 3 节的算术直接给出它。这一对面的权重是 1.0 + 0.7，所以一个两面
都收录的文档只要在两个面里的名次好于

```
1.7 × (60 + 1) / 1.0 − 60 = 43.7
```

就赢过单面第一名——而候选深度是 50。**在 50 个候选里，名次 1 到 43 的双面文档，每一个
都排在任何单面第一名前面。** 观察到的样例正是这个形状：`大概2022年正在学习网页编程
存的`，一个 `lex_seg` 排第一的文档落到融合第 17 位，被 **16 个两面都收录的文档**越过。

### 4.2 真正要紧的是 gold 目标

上面数的是"任何单面第一名"，其中很多本来就是噪声。真正决定召回的是**正确答案**的
遭遇（分母是那 470 条进入融合的查询）：

| | 数量 |
|---|---|
| gold 不在任何一个词面列表里 | 171 |
| 两个面都收录 | 271 |
| 只有一个面收录 | 28 |
| 某个面把它排进前 5 | 244 |
| ——其中被融合挤出前 5 | **15** |
| 只有一个面排进前 5 且被融合丢掉 | **7**（另有 4 条幸存） |

最后一行 n = 11，**小到不能承载任何判定**，但方向和 2.3 的"13 保 8"、4.1 的 79.4% 一致。
样例（面内名次 → 融合后名次）：

```
关于阿耳忒弥斯的图片      lex_tri  #1 → #28
何时程序员选择退休        lex_seg  #1 → #23
create a q a system       lex_seg  #1 → #15
保存有用的网页链接        lex_seg  #3 → #11
automate c++ code checking lex_tri #5 → #38
```

## 5 这改变 W2 什么，不决定什么

### 5.1 改变的：处置顺序

词面审计已经把 `C_lowlex`（降权）从"首选修法"降级成"减损方案"。这一页再加两条：

1. **`C_notri` 已经实现**（`EXPLORATORY` 里，默认关闭）。第 2 节给了它一个理由——
   `lex_tri` 的边际贡献与零不可区分——但**也给了它一个反对理由**：13 条独有命中。
   它上不上，由新查询集说了算。
2. **融合规则本身是第一顺位**，而且第 3 节把"该试什么"从一句直觉变成了一个带数的
   设计约束：任何补丁都必须解决"两个满权重面的联合召回必然压过单面确信"这一条，而
   在纯加性打分里做到这点需要 λ > 1 的 max 项。这直接指向 CombMAX / 分数归一化融合 /
   候选级择一这一类方案，而不是继续调权重。

档位现在一共 **12 个探索/诊断档**（`CONFIGS` 仍是 A–E 五个）：本轮新增
`seg_only`、`tri_only`、`C_notri`。

### 5.2 不改变的

- **W1 的三条预注册判定一条都没有重开。**
- **没有报告任何 W2 新开关在这 479 条上的胜负**，也不会——这批查询产生了这些假设，
  在它上面测这些假设只能测出循环论证。
- **除 `build_fts_query` 的 bug 修复外，默认行为没有改动。** 新档位全部默认关闭。
- 第 2、4 节的效应量都伴随宽置信区间和小 n，**不足以支撑"删掉某个面"这类不可逆决定**。

### 5.3 还欠着的

新查询集尚未生成（缺 chat 模型权重）。在它到位之前，本页第 2、4 节是**描述**，第 3 节是
**算术**，两者都不是判定。判定留给一个没见过这些假设的查询集。
