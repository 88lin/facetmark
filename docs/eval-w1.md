# W1 评测：真实模型、真实网页上的 P1 决策闸门

> 状态：语料与查询集已就位，消融结果待填（见 §7）。本文件随实验推进更新。

## 1. 这份报告在回答什么问题

facetmark 的赌注是：书签检索里，**内容相似度不够**——用户记得的往往是"这页当时是干什么用的"（意图）和"我大概什么时候、在干什么的时候存的"（情境），而不是页面写了什么词。系统为此加了意图面和情境面，代价是每条书签一次 LLM 抽取、一套会话聚类和一张关系图。

这个赌注在 v0.1.0 之前一次都没有在真实模型 + 真实网页上验过。所有模型调用只在 `MockProvider` 下跑过，而 mock 的"嵌入"是词法哈希——`eval/harness.py` 自己的 docstring 就写着"这是管线检查，不是质量测量"。

所以先跑证伪实验，不做任何打磨。判据是设计报告 §13.5 定下的三条，原文照搬，不在事后放宽：

| 判据 | 通过线 | 含义 |
|---|---|---|
| C−B 在 `q_vague` 上 Recall@5 | ≥ +10pp | 意图面对模糊查询有独立贡献 |
| D−C 在 `q_episodic` 上 Recall@5 | ≥ +10pp | 情境面对情景查询有独立贡献 |
| E vs A 在 `q_content` 上 | 不显著劣化 | 四路融合没有把最擅长的场景做坏 |

不通过就如实写"F2 未通过闸门"，默认配置降级为 B（内容 + 词面 + RRF），意图面/情境面改成实验性开关。负面结果照发。

消融梯子每档只加一个机制，差值才归得了因：

| 档 | 组成 |
|---|---|
| A | 只有内容向量（业界现有工具的做法） |
| B | A + 词面（分词索引 + 三元组）+ RRF |
| C | B + 意图向量 |
| D | C + 上下文乘子 + 一跳图扩展 |
| E | D + LLM listwise 重排 |

## 2. 实验装置

沙箱内自建 OpenAI 兼容端点，不需要任何 API key，不接触用户的真实书签：

| 角色 | 模型 | 参数 |
|---|---|---|
| chat | Qwen2.5-3B-Instruct Q4_K_M | `-t 16 -c 98304 --parallel 16 --cont-batching` |
| embed | BGE-M3 f16（1024 维） | `--embeddings --pooling cls -c 8192 -b 8192 -ub 8192 -t 14` |

前面一个极小的路由把两个端口合成一个 `base_url`，因此**业务代码一行没改**——`providers.py` 只认一个 `base_url`，`FACETMARK_EMBED_DIM=1024` 由 `db.py` 与 `providers.py` 的双向校验保护。

机器是 16 核 / 32 GB，无 GPU。实测吞吐：单请求 prefill 204 tok/s、decode 37 tok/s；意图抽取每页 prompt 约 1600 token、输出约 293 token。并发扫描（4 / 8 / 16）得到 286 / 377 / 384 条每小时——**吞吐由 prefill 主导，CPU 已算力饱和，加并发救不了**（16 槽相对 4 槽只有 1.34 倍）。全库实测 370–630 条/小时，随并行任务争抢波动。

**这个装置的偏置方向是压低 C 档**，这一点必须写在结论前面：3B 量化模型的意图抽取质量低于 GPT-4o-mini 一档，而 C 档正是靠意图抽取吃饭的。也就是说，如果 C−B 通过了，换更强的模型只会更好；如果没通过，还需要一轮"是模型不够还是理念错"的判别（抽 50 篇人工读抽取输出）。这是有意选的保守方向。

## 3. 语料

真实书签不能用于评测——不联网、不入库、不进仓库是这个项目对用户数据的承诺。所以另造一套**真实公开网页**的替身语料，分布对齐真实库的实测形态。

来源都带真实时间戳（情境面依赖时间聚类，伪造的时间戳会让 D 档测的是自己的构造）。最终 manifest 的 2376 条来自两处：**阮一峰《科技爱好者周刊》第 191–406 期归档 1807 条**（每期一个批次，中文描述 + 大量英文正文），**Hacker News 公开 API 569 条**。抓取遵守 robots.txt（本轮为此新增了 `fetch/robots.py`，见 §8）、每 host 0.5 秒间隔、真实 UA。

**语料只落 manifest（URL + 时间戳 + 来源），正文不进仓库**，任何人可以按 manifest 重抓复现。

## 4. 语料与真实书签库的五处偏离

评测报告的价值取决于它对自己的局限有多诚实。这五处偏离都会影响结论的外推范围：

**其一，中文分层不一致。** 标题层 57.7% 是中文，正文层只有 9.5% 被检测为中文。原因是周刊用中文描述英文文章——中文标题 + 英文正文是真实存在的结构，但意味着 content 面上大量是跨语言匹配。BGE-M3 是多语模型，能处理，但这不是单语库的形态。

**其二，保存时间戳是构造的。** 页面是真的，批次日期是真的，但"保存时刻"由批次派生（聚簇批次内相邻 45–300 秒，单例保存强制与邻居间隔 >1800 秒）。真人保存节奏比这更不规则。

**其三，会话纯度提升 0.9x，低于 1.0。** 文件夹归类与批次结构在这份语料上互相独立，因此自适应 eps 选择器无法在此语料上被评测（它选了 14400 秒）。D 档用到的会话边本身仍可评测：聚类得到 240 个会话，构造时的批次是 234 个（中位 8 条、最大 74 条），量级吻合。

**其四，抓取存活 79%。** 500 条死链加 324 条待走浏览器通道的页面没有正文，它们仍在库里当干草堆，但不会被选作查询目标。

**其五，`q_vague` 的丢弃率约 40%**（见 §5）。保留下来的是"3B 模型在约束下能造出来的模糊查询"，不是人类模糊性的随机样本。

## 5. 查询集是怎么造的

查询集是这次实验唯一的输入。三条判据全部是"某类查询上的 Recall@5 差值"，所以查询集写坏了，闸门的结论就是关于查询集的结论，不是关于系统的结论。生成器迭代了四轮，**每轮都靠人工读输出发现下一个问题**——自动指标看不出这些毛病。

**v1 → v2**：`q_content` 就是标题原文（所有档 100% 命中，类型不携带信息）；`q_episodic` 退化成裸日期；`q_vague` 是标题直译（组合泄漏，单词各自都不稀有，稀有词闸门放行）。

**v2 → v3：模型不会算相对日期。** 5 个冒烟目标的 5 条 `q_episodic` 时间全错（2022-06 写成"2023年夏天"，2026-05 写成"去年夏天"，2024-08 写成 "last spring"）。错日期比没日期更糟——它把 D 档的信号变成反信号，闸门会假性失败。

修法是**时间表达不由模型写**：Python 从 `date_added` 算粗粒度短语，模型只写话题线索，Python 拼接；然后用**产品自己的 `understand.classify()`** 解析拼好的查询，解析不出包含保存时刻的时间窗就丢弃。错日期从"不太可能"变成"构造上不可能"。相对时间词候选直接从 `understand._RELATIVE` 推导，再叠一层日历正确性检查（"去年" = 上一日历年，"最近" = 90 天内，等等）——只做窗口包含检查会让"前年"贴到 35 个月前的页面上。离线全月扫描 330 个组合 0 失败。

**v3 → v4：few-shot 示例在污染输出。** "人造树叶把 CO2 转液体燃料"这一页的 `q_vague` 被生成为"帮人选择一个网络库"，完全是示例题材；模板里的示范短语被逐字抄进查询。v2 的中文示例更糟——它描述的页面真的在语料里。修法：每语种 4 组互不相干的虚构示例轮换；反抄袭规则改为"查询里出现示例有、目标页没有的实词就拒绝"；模板删掉一切可逐字抄的示范短语。

`q_episodic` 分三个子类型，因为它们走的是**不同机制**，混在一起的均值不指向任何可操作的结论：

| 子类型 | 时间表达 | 命中要靠什么 |
|---|---|---|
| `year` | 绝对年份（"2024年那会儿收的"） | 时间窗 → 上下文乘子 |
| `relative` | 相对词（"三个月前存的"） | 时间窗 → 上下文乘子 |
| `anchor` | 没有日期，只有情景标记 + 同会话邻居线索 | 只能靠一跳图扩展 |

260 个抽样目标的分布：年份 2022:15 / 2023:29 / 2024:33 / 2025:54 / 2026:129；227 个有同会话邻居；子类型 year 152 / relative 65 / anchor 43；157 个中文标题。

## 6. 泄漏探针

查询集的健全性检查：**纯 BM25（无模型、无向量）能答对多少？** 如果 `q_vague` 在纯词法下就已经很高，说明泄漏闸门没挡住，C−B 会被打成 0，闸门会因为查询集而不是因为系统而失败。

v4 冒烟集（22 条）读数：

| 类型 | n | R@5 | R@10 | 从未进前 50 |
|---|---|---|---|---|
| q_content | 8 | 0.50 | 0.50 | 3 |
| q_episodic | 8 | 0.00 | 0.00 | 7 |
| q_vague | 6 | 0.33 | 0.33 | 4 |

`q_vague` 的 0.33 给 C−B ≥10pp 留出了空间；`q_episodic` 的 0.00 说明时间短语确实不携带词法信号。**22 条只是方向性读数，不是测量值**，正式查询集上要重跑。

## 8. 过程中发现的产品缺陷

这一节记录实验**顺带**挖出的真实缺陷。它们不是评测的目标，但都是评测才暴露得出来的。

**其一，中文年份完全解析不出时间窗。** `understand._ABS_YEAR` 原本是 `\b(19[89]\d|20[0-4]\d)\s*年?\b`。Python 把 CJK 算作 `\w`，所以"2023年那会儿"末尾的 `\b` 永不成立——中文写法的绝对年份一条都解析不出来。既有测试用的是"2023 年的会议记录"（数字与"年"之间有空格），恰好绕开了这个缺陷，这是它长期未被发现的原因。改为前后向断言 `(?<![0-9A-Za-z_])...(?![0-9A-Za-z_])`，允许 CJK 邻接，仍然拒绝 `es2015` / `2024px` / `vue 2` 这类标识符。同时补上了中文数字与英文拼写数字的相对时间（"三个月前"、"a couple of weeks ago"、"十天前"），并加了 4 条回归测试。

**其二，意图抽取偶发 JSON 截断。** 全库 enrich 的失败率约 0.5%，形态是输出被截断在 ```json 围栏内。`parse_json_object()` 本身会剥围栏，所以这是真截断，怀疑是每槽上下文（98304 / 16 = 6144 token）装不下 6000 字符中文正文加输出。处置：不重启服务器，留待第二轮 enrich 补（`enrich_all` 会跳过已有结果的行）。

产品侧已修：解析失败或 provider 报错时，用半长正文（`max(600, body_truncate_chars // 2)`）重试一次，成功的计入 `EnrichReport.rescued_by_shorter_body`。运行到后半程时日志给出了这个猜想的直接证据——`https://www.ghibli.jp/works/` 稳定回 `HTTP 400: request (6211 tokens) exceeds the available context size (6144 tokens)`。这条错误也说明缺陷比原先判断的更一般：截断预算 `body_truncate_chars` 的单位是**字符**，而上下文预算的单位是 **token**，中日文两者近似 1:1，所以一页满预算的 CJK 正文单是 prompt 就能顶穿槽位，连截断的回复都换不到。客户端看不见服务端的槽位大小，算不出正确预算，减半重试是与 provider 无关的最简可行解。本轮索引跑的是修复之前的代码，这些页会在第二轮 enrich 补回。

**其三，图扩展的命中在主指标里恒为 0。** `SearchResponse.ids` 只返回 `hits`，不含 `expanded`——一跳扩展是独立分组，界面单独渲染，刻意不与主列表交织。这是产品上的正确选择，但意味着**按原口径 D−C 只测得到上下文乘子，测不到图扩展**，而 `anchor` 子类型只能靠图扩展。为此给评测框架加了辅助指标 `recall@5+exp`（命中主列表或出现在扩展组即算找到），闸门判据不动，两个数字并列报告。

**其四，评测报告只有汇总、没有原始判决。** 要按 `q_episodic` 子类型分层就得拆成三个查询文件跑三遍，而 rung E 每条查询要付一次 LLM 重排，三倍代价不可接受。改为在报告里落逐条 `rank` / `expanded` / `ms`，与查询列表同序。顺带把 `run_rung()` 里 `[o for o in outcomes if o is not None]` 这行静默过滤改成硬失败——它会缩小召回率的**分母**，把一次失败变成一个好看的数字，这是评测最不能有的失败模式。

**其五，内容向量一旦写入就永不刷新。** 这条是全库索引跑到一半时顺手核对向量质量才发现的，也是本次实验挖出的最严重的一个。

线索来自一个看起来无害的异常：2,376 条内容向量里有 69 条（17 组，最大一组 18 条）字节完全相同。第一反应是嵌入端点的批处理把结果串错了位，于是把同一批文本分别用批量和逐条两种方式重算，两个余弦矩阵逐位吻合（对角线外 0.41–0.58），`zip(chunk, vecs, strict=True)` 的配对也没问题。端点是干净的。真正的原因是**这些书签的标题字面相同**——比如 18 条都叫「介绍文章」。可是标题相同就向量相同，本身就说明向量里根本没有正文。

于是拿真实端点当场重算了几条做对照：

| id | 存量向量 vs 当前 enriched 文本 | 存量向量 vs 仅标题 | 标题 |
|---|---|---|---|
| 321 | 0.4165 | **1.0000** | 介绍文章 |
| 517 | 0.4142 | **1.0000** | 介绍文章 |
| 1126 | 0.6282 | **1.0000** | Hacker News 读者 |
| 2122 | 0.7662 | **1.0000** | Raspberry Pi 5 – 16GB RAM |

全部 2,376 条都是早期冒烟阶段（正文和 enrichment 都还不存在时）写下的仅标题嵌入，之后正文抓下来了、摘要与主题也生成了，向量一次都没有跟着动。

根因在 `embed_content(force=False)` 的候选集条件——`b.id NOT IN (SELECT bookmark_id FROM vec_content)`。它只问「这条书签有没有向量」，不问「这个向量是不是当前文本算出来的」。实测 `len(_content_rows(conn, False, None)) == 0`，而 `force=True` 时是 2,376。

这不是实验操作失误，是产品的真实故障路径：用户先 `facetmark index --no-fetch` 建个只有标题的库（文档里就是这么建议先试水的），过几天再 `crawl` + `index` 补正文，内容向量会永远停在标题那一版。`facetmark reindex` 走 `force=True` 能救，增量路径救不了，而且没有任何地方会告诉用户向量已经过期。

本次的处置是外科手术式的：已确认 `enrich_all` 与 `enrich/pipeline.py` 完全不触碰 `vec_content`（grep 无匹配），所以在运行中的索引进程之外直接 `DELETE FROM vec_content`，让它稍后自己调用的 `embed_content(force=False)` 把 2,376 条按当前文本全部重算——不必 kill 进程，已完成的 enrichment 一条不浪费。必须赶在 `filter_intents` 之前做完，因为它内部用 `knn_content` 打探针，拿仅标题的陈旧向量会把大量意图查询按「这一面没信号」误杀，而那是查询集的来源之一。

产品侧已修，schema 迁移 v3：新增 `vec_content_meta` 记下每条向量所嵌入文本的 sha256，`force=False` 比对指纹而不是比对存在性，不一致就重算，`facetmark stats` 报 `content_vectors_stale`。指纹里混入一个 `CONTENT_RECIPE` 常量，因此改动 `content_text()` 的拼法本身就会让全部旧向量作废——这类「配方变了但缓存没变」的缺陷和本条是同一个形状。迁移刻意**不做回填**：库里已有的向量来源不明，把它们记为过期、下一次 `index` 重建，是这个版本唯一诚实的答案。

**其六，语义边的距离上限卡得太死，95% 的书签一条语义边都拿不到。**

全库索引跑完后按 kind 数边：20,113 条里 session 16,930、same_domain 2,708、supersession 45，**semantic 只有 430 条，且只覆盖 2,376 篇里的 113 篇**。也就是说 D 档的图扩展目前几乎完全靠会话边和同域边在撑，语义邻居这一路基本是空的——这会直接影响 D−C 差值的解读。

原因是 `edges.SEMANTIC_MAX_DISTANCE = 0.60`。sqlite-vec 在单位向量上的 `distance` 就是 L2，`d = sqrt(2 - 2cos)`，所以 0.60 对应 cosine 0.82，源码注释里的这个换算没错。错的是这个数在 bge-m3 上的含义：实测随机文档对的距离中位数是 1.1306，而每篇文档**到自己第 8 近邻**的距离中位数是 0.9502（p25 = 0.9103）。互 k-NN 的候选边几乎全部落在 0.9 以上，0.60 的闸门把它们成批砍掉。真正相关的文档在这个模型上的余弦是 0.55–0.70，不是 0.82。

**这个阈值必须重新标定，而标定方式在看到新数据之前先固定下来**（上面这组数是在陈旧的仅标题向量上算的，随内容向量重建全部作废，此处只用来说明缺陷的形状）：

> **预注册规则**：`SEMANTIC_MAX_DISTANCE` 取**随机文档对距离分布的第 1 百分位**，四舍五入到两位小数。

理由：距离上限的职责只有一个，就是拒绝「并不比随机更近」的配对；拓扑上的挑选已经由互 k-NN（k=8）做完了。第 1 百分位的含义是「比 99% 的随机配对更近」，它只依赖零假设分布，可以在不看任何标注的情况下算出来。

**这个阈值不会用那 479 条带标注的查询集去调**。可调的旋钮一旦碰了标注集，闸门判据就不再是判据。标定脚本只采样随机文档对与 k 近邻距离，不读查询文件。重建后会如实报出新的边数与覆盖率，无论它是否好看。

顺带一个负面结果，同样值得写下来：**全局的绝对距离下限做不到「查不到就说查不到」**。随机文档对的第 1 近邻分布（中位 0.8667、p90 0.9685）与真实「问题→它自己那一页」分布（中位 0.8211、p90 0.9392）几乎完全重叠——任何能滤掉大部分噪声的绝对阈值，都会同时滤掉大部分正确答案。「无结果」只能靠**相对**机制（首位与该查询自身融合分分布的落差），不能靠绝对阈值。因此不打算给检索面加距离下限。

**其七，抓取的两处工程缺陷。** 都是读代码时发现的，不是评测跑出来的，但都是真实规模才有意义的失败模式。一是 `fetch_many` 用不带 `return_exceptions` 的 `asyncio.gather`，而 `extract()` 的异常在 `fetch_one` 里没有被接住——一个畸形页面足以让同批已经抓好的结果全部丢掉，并且破坏调用方用来对齐 bookmark id 的「结果按输入顺序返回」契约。二是 `crawl()` 要等整批抓完才逐条落库——抓两千条书签是几十分钟别人的带宽，在 95% 处中断，已抓好的正文全部作废，下一次运行把这些请求重发一遍。两条都已修并补了回归测试（后者的测试在旧代码上确实失败：进度回调时已落库条数全为 0）。

**其八，每条意图查询的向量都买了两遍。** `filter_intents` 给每个候选算一次嵌入用来跑自查探针，算完丢弃；紧接着的 `embed_intents` 把幸存下来的那些用**同一段文本、同一个模型**原样重算。本次语料上是约 19,000 次候选嵌入之后再补约 9,500 次，意图面的嵌入账单多出一半。本地端点上这只是四分钟，在计费端点上是三分之一的调用数。已修：过滤器直接存下探针用过的向量，只在内存里保留通过探针的候选，`IntentReport.vectors_written` 报数。

## 9. 复现

```bash
# 1. 起本地端点（llama.cpp，两个模型，一个路由）
# 2. 按 manifest 重抓语料
python scripts/corpus/collect.py --out manifest.jsonl
facetmark import bookmarks.html && facetmark crawl
# 3. 全量索引：顺序不可乱
facetmark index            # enrich -> embed(content) -> filter_intents
                           #        -> embed(intent) -> sessions -> edges
# 4. 生成查询集（时间表达由 Python 拼、由 understand 校验）
python scripts/corpus/gen_queries.py --n 260 --out queries.jsonl
# 5. 候选池探针：确认目标进得了 C 档的池子，否则 D-C 恒为 0
python scripts/corpus/probe_pool.py --queries queries.jsonl
# 6. 消融 + 闸门判定
facetmark eval --no-build --db LIB --queries queries.jsonl --ablation \
    --bootstrap 1000 --concurrency 8 --out eval_ablation.json
python scripts/corpus/analyze_eval.py --report eval_ablation.json
```
