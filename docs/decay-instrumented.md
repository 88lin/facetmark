# 把仪器打开之后：那个够不着的救援阀其实在帮忙

`docs/decay-reach.md` 的 §7 最后一条写着：「**健康检查的覆盖率没有量。**……冷层只有 8 页，
可能有一部分原因是健康数据本身稀疏，而不是页面真的都还活着。」

这份文档去查了那一条。答案是：不是「有一部分原因」，是**全部原因**。1.5.0 那次实验用的
库，`health` 表有 **0 行**——健康检查器从来没在这个库上跑过一次。冷层判定里那一半靠健康
判定的条件从来没有可能触发。

把健康检查真跑一遍，同一个 A/B 重做一次，**1.5.0 的结论翻转**：

| | 1.5.0（仪器关着） | 1.6.0（仪器开着） |
|---|---|---|
| `health` 表行数 | **0** | 2,376 |
| 冷层页数 | 8（0.34%） | **73（3.07%）** |
| 冷层 ∩ 230 个目标 | **0** | **8**（涉及 19 条查询） |
| ΔRecall@5（修阈值的代价） | `+0.0000pp` CI95 `[0, 0]` | **`−1.4610pp` CI95 `[−2.5974, −0.4870]`** |

**新结论：1.4.0 称为「缺陷」、1.5.0 测为「代价为零」的那个够不着的救援阀，实际上正在
帮忙。把阈值修好会让 Recall@5 掉 1.46 个百分点，区间不含零。所以仍然不改
`decay_rescue_threshold = 0.02`——但理由从「反正没用」变成了「它承重」。**

这两句话的区别很重要。1.5.0 说的是「这段代码是死的，删了无所谓」；1.6.0 说的是「这段
代码在意外地做对事，而且现在有东西压在上面」。前者可以随手清理，后者不能。

## 1. 两个恒真的条件

冷层判定要求三条同时成立（`src/facetmark/search/decay.py`）：

1. `open_count = 0`——从未打开
2. `date_added < now - decay_age_days * 86400`——保存超过一年
3. 有被取代的正面证据：一条 `supersession` 出边，**或者**最新健康判定属于
   `("gone", "drifted", "soft_gone")`

在 1.5.0 用的那个库上，**条件 1 对全部 2,376 条成立**。原因不是这些页都没人看过，而是
浏览器书签的 HTML 导出格式里根本不带使用遥测——`open_count` 只可能是 0。条件 1 不筛掉
任何东西。

**条件 3 的健康判定那一半，同样一次都没有机会触发**，因为 `health` 表是空的。CLI 里
`fm health --check` 的入口在、三层判定器（本地探测 → 外部证据 → 综合）在、
`tests/` 里的单元测试也在，但没人在这个库上执行过它。

于是那个「三条件检测器」实际上只剩下**条件 2（老）+ 条件 3 的 supersession 边**在工作。
全库有 supersession 出边的只有 14 条，其中 8 条同时够老——这就是 1.5.0 那 8 页的全部
来历。

`docs/decay-reach.md` §3 写「条件 3 把 1,071 砍到 8，挡掉了 99.25%」，并把这解读成
「这条件是设计里最重要的一环」。这个解读是错的：条件 3 挡掉 99.25% 不是因为它严格，是
因为它的一半没接线。

## 2. 把仪器打开

同一个库文件复制一份（`library-health.db`），跑一遍全库健康检查：

```python
st = get_settings(health_enable_external=False)
conn = fmdb.connect("library-health.db")
rep = asyncio.run(healthmod.check_bookmarks(
    conn, limit=3000, settings=st, now_ts=1785649110, save_recovered=False))
```

2,376 条 URL 分布在 2,038 个不同 host，`FetchPolicy` 默认 concurrency 30 /
per-host 2 / per-host 最小间隔 0.5s / 遵守 robots，全库跑完 **2.1 分钟**，探测 2,336 条。

`save_recovered=False` 是关键：它保证健康检查**只写 `health` 表**，不把重新抓到的正文
写回 `content`。不然 A/B 就不再是 A/B——正文变了，向量和 FTS 也得跟着变，两次运行的差异
就不再只归因于衰减层。

**A/B 干净性逐层验证过**（深度指纹 = 按主键排序后全字段拼接的 blake2b）：

| 表 | 变化 |
|---|---|
| `health` | 0 行 → **2,376 行** |
| `content` | 未变（`a1d23906699308f4`） |
| `edge` | 未变（`afbe3a90a85fc7cd`） |
| `bookmark` | 未变（`40b85b44f995756c`） |
| 向量表、FTS 表 | 逐位一致 |

最新判定分布（每书签取 `checked_at` 最大的那条）：

| 判定 | 条数 |
|---|---|
| alive | 1,899 |
| restricted | 200 |
| unreachable | 85 |
| unknown | 74 |
| gone | 60 |
| drifted | 58 |

`DEAD_VERDICTS` 覆盖的（gone + drifted，本库无 soft_gone）合计 **118** 条。

## 3. 冷层普查：8 → 73

数字全部落在 `eval/cold-census.json`，两个库并排：

| | 仪器关着 | 仪器开着 |
|---|---|---|
| 全库 | 2,376 | 2,376 |
| 条件 1 单独筛出（从未打开） | **2,376（恒真）** | **2,376（恒真）** |
| 条件 2 单独筛出（老于一年） | 1,071 | 1,071 |
| 条件 1+2 | 1,071 | 1,071 |
| 条件 3 走 supersession 边 | 8 | 8 |
| 条件 3 走死判定 | **0** | **65** |
| **冷层（三条全中）** | **8** | **73** |
| 其中仍有 ≥200 字正文（可服务） | 3 | **30** |
| 其中没有可服务正文 | 5 | **43** |
| 已做过健康检查的页 | 0 | 2,376 |

73 条的构成：`gone 37 + drifted 28 + supersession 8`（三类互不重叠）。

冷层从全库的 **0.34% 涨到 3.07%**，涨了 9.1 倍。更要紧的是它第一次**碰到了答案**：

| | 仪器关着 | 仪器开着 |
|---|---|---|
| 冷层 ∩ 230 个目标 | **0** | **8** |
| 受影响的查询数 | 0 | **19** |

8 个冷目标：`848, 1129, 1277, 1454, 1485, 1614, 2258, 2342`（gone 5 条 / drifted 3 条）。

`docs/decay-reach.md` §7 第二条边界写着「`cold_targets` 为空是查询集的性质，不是库的
性质……这大概是这份实验最需要被质疑的一点」。这一条也说对了，只是原因不是查询集——是
仪器。同一批查询、同一个库，把健康检查跑一遍，`cold_targets` 就从 0 变成 8。

## 4. 重跑 A/B

完全相同的探针、完全相同的查询集、完全相同的时钟，只把库换成健康检查过的那一份。
全部数字在 `eval/decay-reach-checked.json`。

| | shipped `0.02` | reachable `0.0` |
|---|---|---|
| Recall@5 | **0.5860** | **0.5714** |
| Recall@1 | 0.4237 | 0.4188 |
| 救援阀打开的查询数 | **417 / 616** | 0 / 616 |

- **ΔRecall@5 = `−1.4610pp`，CI95 `[−2.5974, −0.4870]`**（10,000 次配对自助，seed 20260805）
- ΔRecall@1 = `−0.4870pp`，CI95 `[−1.2987, +0.3247]`（探索性，区间跨零）

区间不含零。方向是负的：**关掉救援阀（也就是让降权按设计生效）会让检索变差。**

分层的 Recall@5 三档全跌：

| 类型 | n | shipped | reachable | Δ |
|---|---|---|---|---|
| q_content | 181 | 0.9061 | 0.8840 | −2.21pp |
| q_vague | 211 | 0.6540 | 0.6445 | −0.95pp |
| q_episodic | 224 | 0.2634 | 0.2500 | −1.34pp |

顺带一个诊断信号：救援阀打开的查询数从 113 涨到 **417**。阀门判据是「最好的**非冷**命中
分数 < 阈值」，冷页变多之后更多查询的最优命中落在冷页上，非冷最高分掉到阈值以下，阀门
就开得更勤。这个数字本身说明冷层已经不再是可以忽略的角落。

## 5. 机制：算术能完整对上

暴露面：

| | 条数 |
|---|---|
| 候选列表（top-20）里出现过冷页 | 256 / 616 |
| 冷页进了前 5 | **93 / 616** |
| 完整列表发生变化 | 256 |
| 前 5 发生变化 | **93** |
| **目标名次发生变化** | **37** |

37 条名次变化按方向拆开——这是整份文档最有信息量的一张表：

| 变化 | 条数 | 细节 |
|---|---|---|
| **目标跌出 20 条列表**（`to = 0`） | **12** | 其中 **10 条原本在前 5**，**5 条原本排第 1** |
| 目标名次上升 | 24 | 21 条只升一名、3 条升两名；**只有 1 条因此进了前 5** |
| 目标从列表外进入列表 | 1 | 排到第 20 名，不影响任何 Recall 桶 |
| 目标名次下降但仍在列表内 | 0 | — |

于是 Recall@5 的变化可以逐条数出来，不需要任何统计：

```
前 5 的净损失 = −10（跌出的）+ 1（升进来的）= −9
−9 / 616 = −0.014610 = −1.4610pp   ← 和 bootstrap 的点估计完全一致
```

Recall@1 同理：`0.4237 × 616 = 261`、`0.4188 × 616 = 258`，差 3 条，`−3/616 = −0.4870pp`。

**这就是全部机制。** 关掉救援阀之后，降权做了两件事：把非答案的冷页往下压（帮了 24 条
查询，但只有 1 条因此跨过前 5 的桶边界，因为把第 7 名推到第 6 名不改变对错），以及把
**答案本身**往下压（害了 12 条查询，其中 10 条直接从前 5 掉出去，5 条是从第 1 名掉出
去）。收益全落在桶内位移上，损失全落在桶边界上。这个不对称是结构性的，不是运气。

## 6. 根因：URL 死了不等于答案死了

条件 3 的假设是「有证据表明这一页被取代了」。健康判定 `gone` / `drifted` 被当成这种
证据。**这个映射是错的**，而且错在 facetmark 的核心设计上：

**facetmark 存正文。** 一个页面返回 404，不代表本地那份正文快照不再是问题的正确答案。
用户问「calibre 支持哪些电子书格式」，答案是那段文字，不是那个 URL 还能不能打开。健康
判定回答的是「这个链接还能点吗」，冷层需要的是「这份内容还有用吗」。前者不蕴含后者。

`drifted` 更糟：它的意思是「远端正文和我上次存的对不上了」。这恰恰说明本地那份快照是
**独一份的**——远端已经改了，本地这份是唯一还保留着原内容的地方。把它降权是反的。

一个显然的补救是**只在没有可服务正文的时候才降权**：`gone` 且 `char_count = 0` 的页，
降权是安全的，因为它既打不开也没内容可给。这个补救**只救得回一半**：8 个受损目标里
4 个（`1129, 1277, 1485, 2342`）的 `char_count` 就是 **0**——它们完全没有正文，却仍然被
检索到并且是查询集认定的正确答案，靠的是标题和词面面（`lex_seg` / `lex_tri`）。

也就是说：**这个库里有一批"只有标题能找到"的答案**，而"有没有正文"这个信号既不能干净地
区分死链，也不能干净地区分无用页。所以这不是一个干净的修法，`cold_census` 只是把
`servable_cold` / `unservable_cold` 分开报出来，让下一个动手的人先看见这件事。

（相关背景：`docs/w4-intent-read.md` 量到本库正文贫瘠的比例是 62.4%，
`docs/query-set-lexical-audit.md` 量到 6.05% 的查询只有词面面能找到。正文缺失在这个库
上是常态，不是异常。）

## 7. 决定

**不改 `decay_rescue_threshold = 0.02`。** 理由第三次改写：

| 版本 | 理由 |
|---|---|
| 1.4.0 | 「改默认排序需要先有预注册协议」——程序性理由 |
| 1.5.0 | 「已经量过了，收益是零」——经验性理由，但仪器没开 |
| **1.6.0** | **「量过了，修它要付 1.46pp。这个意外正在做对的事，但它现在承重。」** |

`tests/test_decay_reach.py` 那 5 条继续钉住现状，**依然故意不修**。它们钉的是「默认档
里这一层够不着」这个事实。现在这个事实旁边多了一句：够不着是幸运的。

同时明确一件事：**这不构成「衰减层设计正确」的证据。** 现在的状态是一个 bug（阈值高于
单面档能达到的最高分）恰好抵消了另一个 bug（把死链当成无用内容）。两个都还在。要真正
修好，得改条件 3 的语义，而那需要新的查询集（见 §9），不是调一个数。

## 8. 局限

三条，按严重程度排：

1. **73 条冷层是上界，不是真值。** 健康检查是用 `health_enable_external=False` 跑的。
   按 `src/facetmark/health/synth.py` 的规则顺序，规则 1（任何外部正面观察都压过本地
   失败 → `restricted`）排在规则 2（本地 404/410 → `gone`）**之前**。关掉外部证据就等于
   拿掉了唯一能把本地失败翻回来的机制，所以本地-only 是**最偏向判死**的配置。开了外部
   证据（reader proxy + Wayback）之后 `gone` 只会更少，冷层只会更小，ΔRecall@5 的绝对值
   只会更小。方向不会翻——`restricted` 不在 `DEAD_VERDICTS` 里——但幅度会缩。

2. **`drifted` 那 28 条噪声大。** drift 判定是拿约 3 天前的正文快照和现在抓到的比，
   `health_soft_gone_length_ratio = 0.30`。三天里正常改版、加 cookie 横幅、A/B 实验、
   甚至抓取时命中不同 CDN 节点，都能触发。这 28 条里有多少是真的内容变了，没有独立
   核验。

3. **一次健康检查，一个时间点。** `health_gone_confirm_days = 7` 的设计意图是「一次
   404 不算死，要连续观察」。这次只跑了一遍，没有第二次观察去确认。真实部署里的 `gone`
   应该比这更保守。

还有一个**没查清的**问题，记在这里以免忘掉：全库健康检查时 stderr 反复打出
`readability` 的 `ValueError: All strings must be XML compatible`（`lxml_html_clean`
的 `drop_tree` 碰到控制字符），但报告的 `errors` 是空列表——异常在上层被吞掉了。这可能
让一部分页的 drift 检测静默失效，也就是说 `drifted` 那 28 条可能既有假阳也有假阴。
没有追下去。

## 9. 新出现的未测边界

**窄化条件 3 需要一批新的查询集，不能在这 616 条上拟合。**

现在有两个候选改法：

- **(a) 把 `drifted` 从 `DEAD_VERDICTS` 里去掉**——只留 `gone` / `soft_gone`。冷层会从
  73 掉到 45，受损目标从 8 掉到 5。
- **(b) 只在没有可服务正文时降权**——`cold and char_count < min_body_chars`。冷层会从
  73 掉到 43，受损目标从 8 掉到 4。

两个都能在这 616 条查询上把 ΔRecall@5 往零推。**这正是不能用这批数据决定的原因**：
候选改法是**看了这批数据的失败案例之后**想出来的，在同一批数据上评估它们等于在训练集
上报测试分。要判定，需要一批独立生成的查询——而且按 §3 的教训，这批查询必须包含
「找那个已经打不开的旧页面」这类意图，否则又会把 `cold_targets` 造成空集。

`ROADMAP.md` 里的处置已相应改写：衰减层条目从「缺陷，代价已量为零」改成「已量，这个
意外在做对的事，但它是**承重的**意外，需要真设计而不是调阈值」。

## 10. 可观测性

这次翻转能发生，是因为有人去查了 `health` 表有几行。为了让下一次不必靠运气，
`cold_census()`（`src/facetmark/search/decay.py`）把三个条件**分开**报，并且给两处静默
失效起了名字：

```
$ fm stats            # library_stats() 的 payload 里多了 cold_layer
$ fm health --check   # 结尾多打一行冷层普查 + 退化警告
```

`degenerate_conditions` 目前会报两种：

| 名字 | 含义 |
|---|---|
| `never_opened_selects_everything` | `open_count` 全库为 0，条件 1 恒真、不筛任何东西 |
| `health_never_checked` | `health` 表为空，条件 3 的死判定那一半不可能触发 |

在 1.5.0 那个库上跑，两条都会亮。这就是整件事本来应该在 1.5.0 之前被看见的方式。
`tests/test_cold_census.py`（17 条）钉住这些字段的语义，包括「治愈」的情形（一页先被
判 `gone`、后被判 `alive`，只看最新判定所以不算冷）。

## 11. 复现

健康检查（约 2 分钟，只写 `health` 表）：

```python
from facetmark.config import get_settings
from facetmark import health as healthmod, db as fmdb
st = get_settings(health_enable_external=False)
conn = fmdb.connect("library-health.db")
rep = asyncio.run(healthmod.check_bookmarks(
    conn, limit=3000, settings=st, now_ts=1785649110, save_recovered=False))
```

或者用 CLI（`--no-save-recovered` 是 1.6.0 新加的，为的就是让 A/B 保持干净）：

```bash
fm health --check --limit 3000 --no-external --no-save-recovered
```

A/B（约 15 分钟）：

```bash
python scripts/decay_reach_probe.py \
  --db library-health.db \
  --queries eval/queries/w2w3-holdout.jsonl \
  --json eval/decay-reach-checked.json \
  --now 1785649110 --age-days 365 --boots 10000 --seed 20260805
```

冷层普查对照（秒级）：`eval/cold-census.json` 由 `cold_census()` 在两个库上各跑一次得到。
