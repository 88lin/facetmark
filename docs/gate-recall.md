# 门控漏响率：结果报告

协议：`docs/gate-recall-protocol.md`（提交在先，可从 `git log` 核对）。探针：v3 查询集
（`eval/queries/v3-holdout.jsonl`）中 `qtype = q_save_action` 的全部记录。原始报告
`eval/gate-recall-eval.json`，判定与次要量 `eval/gate-recall.json`。

## 0 一句话

**16 条探针，门控漏掉 16 条。漏响率 100%，Wilson CI95 [80.6, 100.0]。但 n = 16 低于
协议预注册的 25 条下限，所以按协议只报描述性数字，不下判定。**

## 1 规模与功效

v3 构造协议的 `--save-action-share 0.15` 在 5 块 × 64 目标上只产出 16 条
`q_save_action`（每目标最多一条，模型在「不许用词表」约束下的写法大量被校验器拒绝）。
协议 §2 写死：**接受 ≥ 25 条即执行判定；不足 25 条只报描述性数字，不下判定，把功效
不足写在结论旁边。** 16 < 25，本报告因此是描述性的。

功效不足的量化：16 条全漏时 Wilson CI95 为 [80.6, 100.0]——即便在这个小样本上，
「门控全接住」（漏响率接近 0）与「门控大半漏掉」也已经可以区分；区分不了的是
「漏 80%」与「漏 100%」。配对 ΔRecall@5 的 mde 无法计算（0 对不一致对，公式分母
为 0）——这不是功效问题，是 §3 的结构性结果。

## 2 主指标一：漏响率

逐条 `classify()`（时钟 = 库快照 `created_at` = 1785649110）：

| | 条数 |
|---|---|
| 判为 episodic（门控开火） | **0 / 16** |
| 未判为 episodic（漏响） | **16 / 16** |

**漏响率点估计 100.0%，Wilson CI95 [80.64, 100.00]。**

逐条看，16 条的说法是：put away × 3、tucked away、set aside、filed away、收起来 × 2、
放在一边 × 2、塞进清单/列表 × 2、放进文件夹、留下的、藏起来、从收集的资料里找。
对照 `understand.py` 的 `_SAVE_ACTION`（保存/收藏/存的/存过/存了/书签/上次/那天/我存/
saved/bookmark/bookmarked/i kept/my bookmarks）：**16 条的说法没有一个落在词表里**。
这正是协议 §0 预言的机制——用户表达保存意图的自然词汇大半被征用为触发词，剩下的
门控一个都不认识——现在在对抗性探针上逐条坐实。

## 3 主指标二：配对 ΔRecall@5（A_gatedctx − A）

| | Recall@5 |
|---|---|
| A | 0.1875 |
| A_gatedctx | 0.1875 |

**Δ = +0.00pp，CI95 [0.00, 0.00]，McNemar 0 胜 0 负，p = 1.0。**

这个零是**结构性**的，不是「门控帮不上忙」的测量：门控在 16 条上一次都没开火，
两档跑的是完全相同的代码路径，逐查询 rank 逐条相同（见 `eval/gate-recall-eval.json`
的 outcomes）。它回答的问题是「漏响让这些查询付多少」——答案是**漏响本身不直接付
Recall@5**；它付的是「本可以拿到的上下文乘子没拿到」的机会成本，而机会成本需要
一个门控开火后能赢的对照才能显形，本探针集上不存在这样的对照。

## 4 自检位

协议 §4：未触发子集的 ΔR@5 **必须是 0.00pp**，不为 0 说明实现或评测有问题，结论
作废。本次未触发子集 = 全部 16 条，Δ = 0.00pp，不一致对 = 0。**自检通过。**

## 5 次要量（描述性）

- 触发率：整体 0/16。按 v3 池拆：16 条目标全部落在 body 池（构造时保存动作类查询
  只从有正文的目标生成），无 dead/bodyless 可拆。
- 触发子集 ΔR@5：空集，无数据。
- 基线 Recall@5 = 0.1875（3/16）本身值得注意：这批查询刻意不含任何内容词、年份、
  词表词，是纯「找我保存过的东西」，对内容向量也是最不友好的查询类型。这个数字是
  A 档在对抗性下限上的表现，不与 W1/W2/W3 的任何数字可比。

## 6 按协议 §4 的处置路径走到哪一步

判定表的三行都需要「漏响率 ≥ 50%」或「< 50%」的**判定**，而协议 §2 规定 n < 25 不
下判定。所以：

1. **词表不动。** 协议 §4 的扩词表处置以「门控漏响不合格」的判定为前提；没有判定
   就没有处置。16 条读出的候选说法（§2 列表）**只允许**按协议 §4 的用途使用——
   作为未来扩词表的候选清单，且扩词表后必须同时过漏响关和 361 条精确率关。
2. **已知限制写在这里**：在「找我保存过的东西」这类查询上，现有词表的漏响率下界
   是 80.6%（Wilson CI95 下界，n=16）。这是下界不是点估计——协议 §5：探针说法是
   模型在约束下写的，真实用户词汇只会更多。
3. **要下判定，需要把 `q_save_action` 扩到 ≥ 25 条。** 构造协议不变（v3 已冻结，
   扩充是新一轮生成，走自己的种子和校验），预计还需 2–3 块 × 64 目标。这是本实验
   线唯一的后续动作。

## 7 这份报告不能用来做什么

- 不能用来给门控上线或下线投票——没有判定。
- 不能用来推「这类查询在真实使用中占多大比例」——协议 §5，探针是对抗性构造，
  测单价不测频率。
- 不能与精确率实验的 −18.83pp 相加或相抵——误响与漏响是同一枚硬币的两面，
  两笔账的合并要等 `gate_v3` 自己的预注册跑完（协议 §5）。
