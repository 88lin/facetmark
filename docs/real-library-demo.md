# 一次真实书签库上的端到端演示

**这不是评测。** 别人的书签没有标准答案，所以下面没有一个数字是打分出来的。做这件事只
有两个目的：确认整条发布路径能在一个真实的、1,700 条的库上跑通；以及看看 1.3.0 那次回退
在真实查询上到底长什么样。

数据是仓库根目录里那份 `favorites_2026_8_4.html`（Chrome 家族导出）。产物
`eval/real-library-demo.json`，脚本 `scripts/real_library_demo.py`。

## 导入

```
parsed 1710 / inserted 1701 / merged_duplicates 9 / non_indexable 1
folders 96 / max_depth 4 / timestamp_unit unix_s / missing_dates 0 / warnings []
```

- 9 条重复 URL 被合并成一条（不同文件夹里存了同一个页面）。
- 1 条 `non_indexable` 是一个 `data:image/svg+xml;base64,...` 的书签——某个页面把内联
  SVG 拖进了收藏栏。它被记下来但不进索引，也没让导入失败。这正是解析器该做的事。
- 1,701 条里 https 1,669 / http 31 / data 1，1,513 个不同域名，最大的一家是 github.com
  的 82 条。保存年份 2022:121 / 2023:191 / 2024:235 / 2025:370 / 2026:784。
- 92.8%（1,579 条）的标题含中文。

## 索引

只跑了 `--no-fetch`：**没有抓取任何页面正文**。1,700 条全部拿到内容向量（bge-m3，对象是
标题加文件夹路径），会话 322 个、边 9,132 条（semantic 4,968 / session 3,218 /
same_domain 938 / supersession 6 / anchor_sibling 2）。

这个覆盖度**恰好够跑出厂默认值**：1.3.0 的 `FULL` 是 `content + graph + decay`，要的就是
内容向量、边和保存时间。意图侧只富集了 20 条（LLM 富集在这台机器上约 17 秒一条，1,700
条要七八个小时），所以任何用到 intent 面的探索档在这个库上都还不能看。

## 检索

12 条查询，中位延迟 2.26 秒（几乎全部是本地 bge-m3 编码查询串的时间，CPU 单机）。

**标题里就有答案的时候，很准。** 「网盘直链解析」→「网盘直链云解析」第一；
「chrome 插件下载」→「Chrome插件下载器」第一，前五里四条来自同一个「插件搜索工具」
文件夹；「视频解析 去水印」前四条全部来自「视频/音乐解析」文件夹；「AI 提示词」前四条
全部来自「AI图片提示词」。

**标题里没有答案的时候，就露馅了。** 「把文字稿变成 PPT 的工具」把「文字转手写工具」排
第一，真正对的「命令式一键生成PPT」排第三——两个标题都含「文字」和「工具」，而没有正文
可以区分它们。「hexo 博客主题美化」前两名是「代码美化截图」和「截图美化」，对的
「Butterfly主题美化教程」排第三：「美化」这个词在标题层面被截图工具占满了。这是
`--no-fetch` 的直接代价，不是排序的锅。

## 回退在真实数据上长什么样

12 条里有 3 条触发门控，其中**两条带年份的主题型查询全部触发**（2/2），和 361 条对抗探针
上的 361/361 是同一回事。最干净的一例：

**查询「2025 日历」**（这个人的库里真有一条「中国2025日历」，存在「工具」文件夹）

| 排名 | 1.3.0 出厂默认 | 1.2.0 带门控默认 |
|---|---|---|
| 1 | **中国2025日历** | 全球日落时间查询 |
| 2 | 免费机场推荐 2025 年 9 月 | 苹果免费ID共享站-2025/11/28 |
| 3 | 全球日落时间查询 | **中国2025日历**（原第 1） |
| 4 | 苹果免费ID共享站-2025/11/28 | 大学生招聘会2025年全国招聘会大全 |
| 5 | 马年春节互动合集 2026 | 免费机场推荐 2025 年 9 月 |

门控把「2025」读成"这个人在 2025 年存的"，于是给 2025 年前后保存的书签加权，把一条与
「日历」毫无关系的「全球日落时间查询」推到第一，把唯一对的答案压到第三。前五重叠 4 条，
但第一名换了。另一条「2024 年的开源模型」触发后第一名没变，前五重叠 3 条。

这就是 −18.83pp 在一条真实查询上的样子。

## 顺带发现的一个反向问题

「上次存的那个签到脚本」**没有**触发门控（`rule_hits` 为空）。「上次」在 `gate_v2` 新加的
`_SAVE_ACTION` 词表里，但不在 v1 的 `_VAGUE_EPISODIC` 里，而这条查询没有年份也没有相对
时间词，所以 v1 判它不是情景查询。也就是说 v1 门控在**该响的时候也会漏**——这次预注册
实验只测了它误响的一面。（这条查询本身结果还不错，「登仙 API 签到」排第一，是内容向量
自己找对的。）

漏响率同样需要一个不是我边看结果边写查询的查询集才能量。记进 W4，和 `gate_v3` 一起。

## 这个演示测不到什么

1. **没有标准答案。** 上面所有"对/不对"都是我读着标题判断的，会偏向我看得懂的那几条。
2. **没有正文。** 全库零抓取，所以这不能代表装上 facetmark 正常用一段时间之后的效果，
   只能代表第一次导入、还没爬完时的效果。
3. **意图面基本是空的**（1,700 条里富集了 20 条），所以融合档、意图检索、`D` 系列在这个
   库上都还没法评价。
4. **一个人、一个库、一台机器。** 2.26 秒的延迟里绝大部分是本地嵌入模型编码查询，换成
   远程 embedding 或更小的本地模型会完全不同。
