# 协议：经 karakeep 桥接回填的库，排序还是不是原来那个排序

**这一页在跑任何一次检索之前写完并落盘。** 判据、样本、指标、判定规则全部写死在下面，
结果追加在 `docs/karakeep-roundtrip.md`，中间不回头改这一页。

---

## 1. 为什么要做这件事

`docs/karakeep.md` 给这次集成写了一句价值主张：

> `POST /karakeep/search` 接受 `config` 参数，所以消融可以在一个真实 karakeep 库上跑。

这句话有一个没被检验的前提：**经桥接回填进来的库，跑出来的排序要和 facetmark 自己
建的库一样。** 如果不一样，那么在 karakeep 库上跑出来的任何消融数字都不能拿回来和
`docs/gate-w1.md`、`docs/gate-w2w3.md` 的数字并排放——它们量的是两个不同的系统。

这件事必须现在做，不能等到有人真拿它去跑消融。

## 2. 已知的结构性差异（在看数据之前列出来）

桥接**只做**四件事：写 `bookmark` 行、写 `content` 正文、写 `enrichment` 摘要与主题、
嵌入内容向量。它**不做**的事，逐条列在这里，因为每一条都可能改变排序：

| 原库有 | 桥接后有没有 | 会影响什么 |
|---|---|---|
| 意图向量 9,475 条 | **没有** | `C`/`D`/`E` 档的意图面全空 |
| 图边 26,697 条 | **没有** | `full`/`D`/`E` 档的图扩展无边可走 |
| 会话 240 个 | **没有** | 上下文乘子的会话信号恒为 0 |
| 内容正文 1,876 篇 | 有（逐字复制） | — |
| 摘要 / 主题 | 有 | — |
| `date_added` | 有（ISO 8601 往返） | 时间衰减、时间窗 |

所以**这次只对能公平比较的那一档下判定**：`A`（只有内容面）。`full` 档同样测，但
**不设判据**——它含图扩展，而桥接后的库没有边，测它是为了量出「不补跑
`facetmark index` 会亏多少」，那是一个要写进文档的数字，不是一次胜负判定。

## 3. 样本

| 项 | 值 |
|---|---|
| 源库 | `/workspace/w1/library-w1-indexed.db`（W1 语料，2,376 篇） |
| 回填对象 | **全部 2,376 篇**，含 500 篇无正文的 |
| 为什么是全部 | 候选池必须一模一样。只回填有正文的 1,876 篇会把池子缩小 21%，桥接库会因此**平白**赢，那是抽样偏差不是保真度 |
| 查询集 | `eval/queries/w2w3-holdout.jsonl`，**616 条**，与 `docs/gate-w2w3.md` 同一批 |
| 为什么用这一批 | 它没有参与产生桥接代码里的任何决定；而且它的十档基线已经落盘，可以横向对照 |
| 打分口径 | 按 `target_url` 匹配，不按 `bookmark.id`——两个库的自增 id 必然不同 |
| 嵌入模型 | bge-m3（本地，f16，dim=1024），两侧同一个模型同一份权重 |
| 时钟 | 固定 `now_ts = 1785649110`，与 `docs/gate-w2w3.md` 一致 |
| bootstrap | 10,000 次配对重采样，seed 20260803 |

## 4. 文档映射（桥接输入怎么造出来的）

每篇源页面造一条 karakeep 文档：

```
id           = "w1-<bookmark.id>"
userId       = "roundtrip"
url          = bookmark.url
title        = bookmark.title
content      = content.body_text（没有正文就是空串）
summary      = enrichment.summary
tags         = bookmark.folder 按 "/" 切开（W1 语料的 folder 基本为空）
createdAt    = bookmark.date_added 转成 ISO 8601 UTC
description  = ""（W1 语料没有这个字段的对应物）
note         = ""（同上）
```

`description` 和 `note` 留空是**故意的**：桥接把 `description + note + content` 拼成一块
存进 `content.body_text`，留空之后拼接结果逐字等于原正文。这样这次测的就是**管道保真
度**，不是**文本映射保真度**。后者需要一个真实的 karakeep 库才测得了，这里测不了，写在
第 7 节。

## 5. 两个比较，分开做

桥接有两条路径，混在一起测的话，出了差异分不清是谁的：

- **写路径**（`addDocuments` 怎么把文档写成 facetmark 的行）：比较 **原库原生 `search()`**
  与 **桥接库原生 `search()`**。两边同一段代码、同一个时钟、同一批查询，唯一的变量是库
  是谁写的。**判据 a 和 b 判的是这一条。**
- **读路径**（`POST /karakeep/search` 的 id 映射、`OVERFETCH`、过滤、时序分支）：比较
  **桥接库原生 `search()`** 与 **桥接库经 HTTP 的 `POST /karakeep/search`**，同一个库。
  这一条应当**逐条完全一致**，因为读路径只做 id 翻译，不改排序。**判据 c 判的是这一
  条**，见第 6 节。

## 6. 指标

对每条查询、每个档位、每个库：

- `hit@1`、`hit@5`：目标 URL 是否落在前 1 / 前 5
- `overlap@5`：两个库前 5 名的 URL 交集大小（0–5）
- `top1_same`：两个库第 1 名是不是同一个 URL

汇总：Recall@1、Recall@5、ΔRecall@5（配对）、CI95、McNemar 精确双侧检验、
overlap@5 的中位数与分布、`top1_same` 比例。

## 7. 判定规则（看结果之前写死）

写路径只对 `A` 档判定（`full` 含图扩展，桥接库没有边，不可比），读路径对 `A` 和
`full` 都判：

| # | 路径 | 判据 | 通过线 |
|---|---|---|---|
| **a** | 写 | 指标层面保真 | ΔRecall@5 的点估计 \|Δ\| ≤ 3.00pp **且** CI95 完全落在 [−5pp, +5pp] 内 |
| **b** | 写 | 列表层面保真 | `overlap@5` 中位数 ≥ 4，**且** `top1_same` ≥ 80% |
| **c** | 读 | HTTP 路由不改排序 | 616 条查询 × 2 档，`POST /karakeep/search` 返回的 URL 序列与同库原生 `search()` **逐条完全一致**，允许 0 条不一致 |

- **a、b、c 全过** → 判 `roundtrip_faithful`：在桥接库上跑出来的 `A` 档消融数字，可以和
  本仓库既有的 `A` 档数字并排放。
- **任一条不过** → 判 `roundtrip_unfaithful`：`docs/karakeep.md` 里那句价值主张必须
  撤回或者加限定，而且要把不过的那一条写进 README。

判据 c 允许 0 条不一致，是因为读路径按设计只做 id 翻译。任何一条不一致都说明
`OVERFETCH`、过滤或者时序分支在改排序，那是 bug 不是噪声。唯一被豁免的是**分数完全
相同时的平局次序**：若两侧前 5 的 URL 集合相同而顺序不同、且交界处分数逐位相等，记为
`tie_reorder` 单列，不计入不一致。

**判据 a 为什么是 ±3pp / CI 落在 ±5pp 内。** 两个库的内容向量由同一个模型对同一段文本
编码，理论上应当逐位相同；能造成差异的只有浮点非确定性、行插入顺序影响的 KNN 平局
决胜、以及 `sqlite-vec` 的近似。这些应当产生**接近零**的差异，所以 3pp 是一条宽松的
线——它宽松是故意的：这条判据要抓的是「桥接漏了什么结构」这种量级的错，不是小数点后
第三位。n=616 时，这批查询上过去测到的最小可检出效应（mde）在 2pp 量级，所以 3pp 这条
线是可检验的，不是空头支票。

**判据 b 为什么要单独存在。** Recall@5 只看目标在不在前五，对「第 5 名换到第 1 名」
完全瞎——`docs/gate-w1.md` §7.2 已经在重排器上撞过这件事一次。两个库可以有一样的
Recall@5 而前五名几乎不重合，那种情况下「排序一样」是假的。

## 8. 这一次测不到什么

写在结果前面，因为结果出来之后再写就会挑着写：

1. **TypeScript 那一侧完全没被碰到。** 这次是直接对 `POST /karakeep/documents` 发
   HTTP，绕过了 `integrations/karakeep/search-facetmark`。那个插件在本仓库既不构建也不
   测试（没有 Node 工具链）。它有没有正确实现 `SearchIndexClient`，这次一个字都没测。
2. **真实 karakeep 的文本没被测到。** karakeep 用无头 Chrome 抓、自己抽正文；这里喂进去
   的是 trafilatura 抽的。同一个页面两边抽出来的文本不一样，而**文本不一样排序就会不
   一样**，那个差多大这次量不了。
3. **多用户没被测到。** 全部 2,376 条挂在同一个 `userId` 下。`userId` 过滤发生在排序
   **之后**这个已知缺陷，需要一个多用户库才测得出偏差有多大。判据 c 只在单用户下测读路径，`OVERFETCH` 在多用户下的行为不在其内。
4. **意图面没被测到。** 桥接不填意图向量，所以 `C`/`D`/`E` 档在桥接库上必然更差，这不是
   桥接的 bug，是「回填之后要补跑 `facetmark index`」这条使用要求。这次只量 `full` 档，
   给出这条要求的价目表。
5. **增量更新语义没被测到。** 这次是一次性全量推入。karakeep 真实运行时是增量
   `addDocuments` + 偶发 `deleteDocuments`，长期漂移这次看不到。
