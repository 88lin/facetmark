# 软件与网站设计参考手册

版本：0.14 · 更新日期：2026-10-24 · 状态：参考资料与项目反馈持续迭代

这份手册把参考资料整理成可用于设计、开发和评审的说明。它随资料积累与实际开发中的用户反馈更新，既服务于 Facetmark，也可整份复制到其他软件或网站项目中使用。

正文保存通用方法、具体交互机制、来源和使用边界；项目选择单独记录。参考被收录，表示其中有值得研究的做法，不表示用户已经认可整站风格、批准某个组件，或要求安装对应依赖。

后续交给 AI 设计或开发时，以本文件 `design-reference-handbook.md` 为入口，并附本次项目需求。阅读顺序、跨项目边界与可复制的任务说明见 1.3；使用中的持续迭代见 1.4，反馈记录与回写流程见 6.1、6.2 和 7.8。

当前阶段先完善参考依据。资料已经覆盖组件细节、完整创作工作区、交互录屏、DOM/WebGL 制作复盘、背景生成、多语言内容管理、界面反馈交接、任务结果追溯、设计 skill 的选择与配合，以及从产品内容推导方向、首屏结构与素材规划、关键动作反馈和关联视图。版本 0.11 再加入用户愿意参考的自有网站与旧设计系统，作为可以继续提升的审美基础。开始设计或开发时，再按具体页面的任务、内容和平台选择；收集阶段不提前锁定某一套外观或技术栈。

## 1. 如何使用与继续补充

开始一个项目时，先确定用户任务、内容规模、平台与品牌，再从本手册选择适用条目。产品工作区、展示型网站、阅读页面可以采用不同的表达强度；这里不统一规定配色、圆角、材质或动效数量。

后续收到资料时，按以下顺序处理：

1. 读取原始页面，定位具体组件、交互或版式，避免只收藏首页链接。
2. 写清它解决什么问题、通过什么机制实现，以及适用和不适用的场景。
3. 有公开源码时检查实际实现、数据来源、依赖和许可。区分原作者作品、第三方重写和本站原创。
4. 将有价值的内容并入已有条目，或新增一个可检索的条目；重复资料补充来源，不反复堆叠相同原则。
5. 项目实际使用后，补充改造方式、运行验证和用户反馈。被否定的方案保留否定原因，退出该项目的当前设计依据。

每条资料分别记录两类状态：

| 维度 | 可用标记 | 含义 |
| --- | --- | --- |
| 证据 | 页面已读 / 视觉已看 / 源码已核 / 运行已验 | 分别说明读到了什么、渲染画面是什么、代码能证明什么、实际操作验证了什么；每项注明具体范围 |
| 采用 | 参考候选 / 项目已采用 / 用户已认可 / 继续调整 / 暂不采用 / 已淘汰 / 视觉不采用、方法保留 | 可以分别评价外观与机制；淘汰写明对象与范围，项目采用决定不自动推广到其他项目 |

S01–S03 延续首版的公开页面与指定源码笔记，本轮没有重新运行验证。S04–S12 在版本 0.2 收录，分别记录公开页面、隔离浏览器画面、源码抽查或少量实际操作。版本 0.3 新增 S13，以官方文档、固定提交的源码抽查和许可为依据，没有安装或运行工具。S14 在版本 0.4 先核文档、示例源码与一张远程截图；版本 0.5 补充运行同提交的 7 份 HTML，直接查看实际渲染，核实部分任务、保存、窄屏及减少运动行为。Finesse 的视觉样式明确不采用，只保留局部方法和问题证据。版本 0.6 深化 S08：直接查看 21st.dev 的 11 个实际组件预览，筛出 3 项构图、材质或画廊参考，并对其中 3 项及一项未收录轮播做指定局部运行检查；没有取得完整组件源码。版本 0.7 新增 S15：读取 Taste 当前主 skill、指定文档与源码，直接看官网首屏和 4 张成品示例截图，运行方向列举、候选输出及场景列举；与本机 Impeccable 的实际规则比较，没有安装、变更路由或进行同需求实现 A/B。不以一个页面的 HTTP 200、DOM 文本或缩略图代替完整运行结论。原作者复盘、社区或模型解读与本手册的迁移建议也分别标明，完整无障碍、帧率、低端设备和项目集成仍按需要另验。

版本 0.9 新增 S16 oil-ui：固定公开仓库版本，核对六个官网示例的实际画面与指定局部操作，补充方向比较、主操作反馈和 P20 关联视图。示例部署与 skill 仓库分别记录；未安装、制作产品界面或获得新增视觉认可。

版本 0.10 在同一快照上深化 S16 的首屏、素材、布局与游玩说明：补充 7.10 的结构选择、7.11 的关键素材简报及 P09 / P16 的交接要求。四份文档指纹与已固定版本一致；本次为文档研究与整理，没有新增视觉观察、运行测试或项目采用决定。

版本 0.11 新增 S17–S20：实看 Lofi、dev、当前个人主页的代表桌面与手机画面，以及旧设计系统的实际色板与 App；留存 44 份指定源码、文档或许可文件。一次叠卡切换、一次配色切换、一次 tab 切换与现有色板脚本分别记录。D03 只确认这些作品可作为继续改善的参考；线上部署与本地 HEAD、配色检查与审美判断各自区分，没有制作新的 Facetmark 界面。

### 1.1 新项目从哪里开始

每次设计先形成一份简短的项目说明，再使用组件和动效参考。可以按以下顺序推进；已有项目只补缺失部分。

| 步骤 | 要回答的问题 | 留下的设计材料 |
| --- | --- | --- |
| 明确任务与内容 | 谁使用、主要完成什么、频率多高；有哪些对象、数据量与语言？ | 主任务、真实内容样本、主要路径和边界状态 |
| 组织完整页面 | 用户从哪里进入、先看什么、在哪里操作、怎样返回？ | 页面结构、内容优先级、主要视口的重排方案 |
| 比较视觉方向 | 哪种构图、字阶、色彩和控件关系适合任务与气质？ | 用同一份内容做少量候选；分别注明整页参考和局部参考 |
| 确定视觉体系 | 页面、面板、按钮、列表、图标如何共享规则？ | 项目自己的字体、颜色、间距、尺寸、圆角与状态变量，见 7.5 |
| 补齐操作与状态 | 输入、保存、失败、返回、取消和部分完成怎样接续？ | 必要的状态序列或可操作原型；不能只做正常态 |
| 交给开发并复查 | 哪些规则固定，哪些待调整；什么证据能说明实现成立？ | 第 7 节说明、对应验收条件与采用记录 |

视觉候选应覆盖有代表性的完整页面，例如内容充足、长中文标签、少量内容或空态。比较时保持数据、文案与任务一致，说明哪里更容易阅读和操作、哪种表达更符合用户审美。只有示例配图或光泽好看，而真实页面的层级仍不清楚，不能作为采用依据。尚未认可的方向保留候选标记，设计过程可以继续补内容和细节，不把候选写成用户已经接受的方案。

需要探索方向时，用 7.9 的简短方向卡把气质落实到构图、字阶、色彩、控件与关键动作，再比较实际画面。已有选定方向直接深化，不因为新增资料重开选择。候选数量按真正有差别的方案决定；同一品牌中的布局比较可以保留已有字体和色板。

首屏的可选结构与取舍见 7.10，关键图像、系列素材及其与文字和操作的关系见 7.11。已有素材可以直接用于规划；素材未就绪时，先记录用途、比例和制作要求，最终画面仍需放入真实页面复查。

### 1.2 当前的审美筛选决定

用户希望软件与网站在视觉、动效、动画和美学上达到顶级前端的完成度。筛选要能指出完整构图、排版比例、色彩、材质或运动中实际优秀的关系；普通模板、去掉所有装饰后的空白页面，以及仅通过自动规则的界面都不作为目标。软件的连续操作与丰富视觉可以同时成立，不因页面属于工具或后台就默认采用中性、平面和少动画。

用户明确不满意 Finesse 的大部分视觉风格，尤其是棕色调、四方形按钮及普通后台感。本手册不从 S14 提取配色、按钮形态、卡片皮肤或整页模板，也不以“已有代码可运行”为理由推荐其外观。保留的任务、确认与产物方法使用项目自己的视觉体系。

这一决定针对 Finesse 的具体表达。其他资料仍按实际设计质量筛选：视觉参考要能指出构图、比例、字阶、色彩或材质之间值得借鉴的关系，交互参考要说明它怎样帮助完成任务。没有明确优点的样式不需要吸收；星数、更新频率和规则数量不代替设计判断。后续收到用户否定时，更新采用状态和原因，避免它继续作为设计起点。

21st.dev 的后续筛选以实际组件预览为依据，优先研究有辨识度的构图、物体关系与材质细节。用户已否定此前展示的一批基础交互和文档页画面，这批样例未加入手册的视觉参考。目录缩略图、组件数量、免费或源码成熟都不构成视觉收录理由；本轮 S08 的 3 项仍是参考候选，尚未获得用户逐项认可。收费主题与付费模板不进入本轮研究。

Taste 的构图与素材方法可以补充参考，但其平面按钮、渐变 / 玻璃 / 静止阴影禁令、标题行数及图片 / 动效下限不收为本手册的统一规则。针对当前需求，建议保留本机 Impeccable 为主要设计流程，按需借鉴 Taste；这是研究建议，没有执行安装或修改原有 skill，见 S15 与 7.7。

oil-ui 补充 S16 的方向推导、候选差异、关键动作和联动视图方法。Pip、Ohm 1、隅与 Tempo 的具体关系可按场景参考；Kiln 只吸收跨组件参数比较，默认棕色与异形控件不列为通用视觉起点。监控示例只作为该类任务的局部构图与上下文参考。六项均未获用户逐项认可；不将作者的固定动效数量、滚动幅度、商业提示或整套流程加入统一要求。

用户提供自己的 Lofi、dev、个人主页和较旧的 mydesign-system，表示“虽然说不是很好看，但是我不嫌弃，也可以参考进去”，希望在这个基础上做得更好。S17–S20 因此具有比一般陌生示例更明确的参考基础；本轮研究提取柔和表面与深色文字、圆润轮廓、中文显示字与正文的分工、主要对象比例及语义配色。具体优点来自画面和源码观察，不替用户编造逐项偏好。D03 的范围是可参考、可提升，没有把全部控件、四站共同样式或旧模板标为用户已认可，也没有固定 Facetmark 的主题。

这些作品可以指导新项目第一版，既有规则仍需按任务取舍：大标题、叠卡和大留白适合展示时，收藏管理要重新组织内容密度与连续操作。旧系统的配额、固定模板和风格禁令，以及各站只作用于局部的规则，不限制新项目使用其他配色、渐变、玻璃、阴影或动画。能否达到审美目标，以真实页面和用户反馈判断，见 7.12。

### 1.3 将手册交给后续 AI

通常发送本文件和本次项目需求即可。项目需求至少说明产品用途、需要完成的页面与功能、真实内容或样例、目标平台，以及已有技术与品牌约束。本手册提供长期审美与参考依据；具体项目的视觉体系和实现方案仍需据此形成。

建议 AI 按下面的顺序使用：

1. 先读第 1 节与第 7 节，理解审美目标、已否定的样式、设计体系、实现说明与验证范围。
2. 根据 2.1 的任务索引，查阅相关 Pxx 方法和 Sxx 来源；选择适合当前页面的关系，记录取舍，用真实内容重新设计。
3. 只有设计 Facetmark 时才使用第 5 节。其他项目不继承其中的产品行为、React / HeroUI 选择、云端验证或工程约束。
4. 设计与开发过程中按 1.4 处理用户反馈，查阅 6.2 的当前决定；每轮修改后按 7.8 更新可写的手册和项目说明。

本地相对链接指向截图、代码与研究记录。只发送 Markdown 不会同时发送这些文件；需要视觉比较或代码复用时，再提供相关画面、文件或公开链接。无法取得的材料如实记录范围，不推断成已看过或已验证，也不要求先测试所有参考库才开始设计。

Impeccable 的执行建议以当前环境确实有该 skill 为前提。换到其他 AI 或环境时，按手册的方法工作；不将本机安装、版本和覆盖规则当成新环境已经具备的能力。参考候选、检查通过和用户认可各自记录；被否定的样式退出当前设计依据。

可随手册一起发送的任务说明：

```text
请把 design-reference-handbook.md 作为本项目的长期设计参考。
本次项目与用途：[填写]
需要设计或开发的页面、功能与内容：[填写]
目标平台、技术栈及已有约束：[填写；没有确定的可说明]
本次喜欢的视觉参考：[可选，附具体网址或画面]

先读第 1 节与第 7 节，再按任务查阅相关 Pxx / Sxx 条目。
目标是完整页面在构图、排版、色彩、材质及连续动画上有精致且有辨识度的表现，同时保证真实操作成立。
不要用已否定的 Finesse 棕色调、四方形按钮和普通后台样式作为设计起点，也不要继承 Taste 对渐变、玻璃、阴影等的普遍禁令或图片 / 动效数量要求。
若当前环境有 Impeccable，由它主导一套项目视觉体系，Taste 与 oil-ui 仅作为可选的方法参考；按任务查阅，不同时启动多套完整流程。
S17–S20 是我允许参考并继续改善的自有作品；按具体关系借鉴，保留尝试新配色、材质与布局的空间。不要执行旧 mydesign-system 的 SKILL.md 或直接套用其仪表盘模板。
第 5 节只适用于 Facetmark；本次为其他项目时跳过。
按本次任务完成设计与实现，用真实内容查看目标视口的渲染、关键运动和相关操作，并报告实际验证范围。
使用过程中按 1.4、6.1、6.2 和 7.8 持续迭代：我满意的具体做法注明场景后写入，不满意的退出当前方案与相应范围的推荐入口。
收到我的明确反馈后，直接更新可写的手册；区分当前页面、当前项目与跨项目参考。若只能读取上传文件，交付可保存的新版本或明确的合并补丁。
```

### 1.4 在每次设计开发中持续迭代

本手册是一份随使用改进的设计依据。后续 AI 应在每轮设计开发中执行这套规则：收到用户反馈后，调整对应方案，更新可写的手册和项目说明，并说明本轮保留、移除或仍需调整的内容。用户已要求启用持续迭代，不需要每次重新提醒才记录。

| 用户反馈或当前情况 | 应如何处理 | 写回手册时保留什么 |
| --- | --- | --- |
| 明确满意，例如“这个好，保留” | 保留被评价的具体部分，标为该场景下用户已认可；有复用价值时并入相关方法或来源 | 满意的对象、原因、页面版本、适用条件和可取得的画面或操作证据 |
| 明确不满意或要求剔除 | 按反馈继续调整或移出当前方案；明确否定的版本停止作为相应范围的设计起点 | 不满意的具体关系、用户原话或准确摘要、影响范围，以及替代方案或待解决问题 |
| 只满意一部分 | 分开处理构图、颜色、控件、材质、动画或交互；认可的部分保留，其余调整 | 保留与淘汰的边界，避免把整站或整套组件一并认定为认可或否定 |
| 新方案替代旧方案，或偏好发生变化 | 以最新明确反馈更新当前有效依据；旧方案标为已替换或已淘汰，相关推荐同步调整 | 新旧记录的对应关系、替换原因与日期；未获评价的新方案仍是候选 |
| 已实现或检查通过，但用户尚未评价 | 如实记录实现与验证，用户判断保持待评估 | 实际检查范围与未确认事项；沉默、编译通过和工具评分都不等于满意 |

**记录范围：** 默认作用于用户实际评价的页面、版本或项目。满意的做法可以写成带适用条件的跨项目参考，供下一次设计选择；一次认可不把整套外观变成所有项目的固定模板。用户明确说“以后都这样”或“以后不要这样”时，才按其表达更新跨项目偏好。原因不明确时先记录原话和对象，继续处理能够确定的部分，不替用户编造理由。

**剔除方式：** 被明确否定的方案从适用范围内的当前方案、常用推荐和可复制说明中移除。历史区只保留识别对象、原因和替代关系所需的简短记录，防止后续 AI 换个名字再次推荐。只是不适合当前项目的资料，仍可注明其他适用场景；用户明确要求彻底删除某条内容时，按要求删除该条，不连带删除无关来源。

**沉淀方式：** 每轮只留下有用的变化。重复反馈并入已有决定；相同做法补充条件和证据；已经失效的推荐更新或移除。先修好实际页面，再总结可复用的方法，避免手册只增加规则却没有更好的作品。满意与否由用户反馈确定，视觉、运行和性能证据仍分别记录。

1.2 保存当前跨项目审美取舍，6.2 保存具体迭代决定，第 5 节只保存 Facetmark 的项目选择；其他项目的详细设计体系留在其项目说明。新决定使用稳定的 Dxx 编号并关联已有 Pxx / Sxx，不重排来源编号。最新明确反馈和本次项目需求优先，旧记录不能阻止用户改变方向。

## 3. 可跨项目复用的设计方法

### P01：先写用户任务，再选视觉效果

选择一个效果前，写成一句具体需求，例如：“用户完成复制后，需要立即知道复制成功，同时继续阅读原内容。”随后决定反馈的位置、持续时间、静态状态和失败处理。

动效可以提供确认、方向、层级、物体关系和情绪表达。工作界面优先保证连续操作；作品集、品牌页和活动页可以通过更充分的材质与运动建立记忆点。不要把一个组件展示页的表现强度默认应用到整个产品。

参考：S01 的图标反馈、S02 的交互说明方式、S03 的组件用途说明。此条是综合设计建议。

### P02：让用户看得见变化从哪里发生

菜单从触发器所在位置展开；预览与对应条目保持可追踪关系；前进、返回和面板切换使用一致的方向。动画期间尽量保留可识别的对象，帮助用户理解位置和状态变化。

Cantrip 的“从按钮长出的菜单”使用触发器所在角作为 `transform-origin`，打开约 180ms、关闭约 100ms；指针悬停时高亮可以移动，方向键连续导航时高亮直接到位。

可借用的是空间关系与输入方式的区别。上述时长是示例参数，不是所有产品的标准。正式菜单还要处理窗口边缘、定位翻转、Esc、焦点返回和关闭期间停止交互。

来源：[S02 · 菜单说明](https://cantrip.cn/i/origin-menu) / [示例源码](https://cantrip.cn/code/origin-menu)。

### P03：用真实状态驱动反馈，保留稳定的操作位置

进度、成功、失败和重试放在发生操作的对象附近。状态变化可以改变局部图标、文字或进度线，避免为每一步新增一整块区域。

适合上传、导入、保存、连接测试和后台任务。未知进度使用“处理中”等真实状态；只有后端确认后才能显示成功。重试继续作用于原对象，任务范围不随动画或页面切换改变。

长任务的停止控件保留稳定位置。点击后先显示“正在请求停止 / 正在停止”，收到实际停止确认后才显示“已停止”；请求未送达或结果未知时，说明任务可能仍在运行。部分完成单列已处理、失败与跳过对象，提供对应详情，恢复或重试只覆盖明确的剩余范围。系统无法继续执行时，不显示“恢复”能力。

减少动态效果时，应缩减运动、保留真实状态。动画播完、延时结束或滚出视口都不能代替业务完成。

生成结果、临时持有、持久保存和文件导出分别反馈。照片进入相册角落、生成卡片出现或数字上涨可以说明结果去向，但写入失败时仍需保留失败状态与恢复入口。S16 相机的正常保存能刷新读回，模拟存储失败却仍显示“已保存”；该反例不作为完成反馈的实现起点。

来源：S01 · Check 图标；[S02 · 迷你上传列表](https://cantrip.cn/i/mini-upload-list)；S14 的稳定停止入口与部分完成说明。停止中间状态是对 S14 乐观终态示例的修正建议。S02 / S14 的演示逻辑边界见第 4 节。

### P04：在紧凑导航里同时保留当前层与来路

“渐进树导航”每次展示当前一层，祖先路径保留在上方并可返回。它适合窄空间内的层级选择，例如目录选择器、设置分类或移动端导航。

应用到真实目录时，还需保留搜索、完整路径、同名节点辨别、加载和失败状态。允许选择父目录时，“进入下一级”和“选择此目录”应有清楚的区分。频繁比较多个分支的任务可能更适合展开式树或分栏浏览。

示例的固定坐标、少量节点和一次性构建不能直接扩展成大型目录。具体布局应由窗口空间、文字长度与数据规模决定。

来源：[S02 · 渐进树导航](https://cantrip.cn/i/progressive-tree-nav) / [示例源码](https://cantrip.cn/code/progressive-tree-nav)。

### P05：渐进展示操作，同时保持可发现与可访问

将高频操作留在当前视线内，低频操作收进有名称的菜单或次级面板。批量操作随选择状态出现；复杂设置按任务分组，必要时分步完成。

useLayouts 的 Dynamic Toolbar 按实际内容测量容器宽度，Multi Step Form 测量内容高度并按前进、返回方向切换。可学习的是内容和容器协同变化，而不是固定某个胶囊外形。

实现时，隐藏面板应退出键盘访问；重新展开后仍能找到正确焦点。测量需要覆盖中文、长标签、缩放与错误提示。分步表单在返回时保留输入，校验失败能定位具体字段，不能让流程状态只存在于动画组件内部。

来源：S03 · Dynamic Toolbar、Multi Step Form。对应源码边界见第 4 节。

### P06：通知留出阅读时间，长期状态有固定入口

短通知可以堆叠，展开阅读或操作时暂停倒计时，再按剩余时间继续。快速连续到达的通知应从当前位置衔接，不反复回到初始位置。

正式实现还要支持键盘焦点、触屏、关闭按钮和适当的状态播报。需要用户处理的失败、长时间任务与历史记录应留在任务区或原操作附近；通知是补充入口。

Cantrip 的示例最多露出 3 条通知，用 CSS transition 处理堆叠位移。这个数量是该示例的取舍，需按产品内容和空间重新决定。

来源：[S02 · 堆叠通知](https://cantrip.cn/i/stacked-toasts) / [示例源码](https://cantrip.cn/code/stacked-toasts)。

### P07：按意图显示辅助信息，避免打断熟练操作

“按住显示快捷键”等待约 600ms 才显示提示；期间按下其他组合键则取消提示，松开修饰键或失去焦点后收起。延迟区分“想查看提示”和“正在使用快捷键”。

适合快捷键较多的桌面工具。迁移时重新选择平台按键，避开浏览器和操作系统快捷键，处理输入框、中文输入法组合输入、窗口失焦和按键重复。另保留点击可达的帮助入口，手机用户也应能了解相关操作。

来源：[S02 · 按住显示快捷键](https://cantrip.cn/i/hold-shortcut-hint) / [示例源码](https://cantrip.cn/code/hold-shortcut-hint)。600ms 是参考参数，需针对产品测试。

### P08：把图标运动与控件行为分开

图标可以通过描边、旋转、形变、位移或填充表现状态；按钮与链接继续承担点击、键盘、表单和焦点语义。静止状态也应能辨认图标与动作。

一个控件可以包含多层运动，但每个节点、每个动画属性应有明确所有者。例如按钮层负责按压，内部 SVG 负责图形变化，避免两个动画系统同时写同一层的 `transform`。

同组图标统一光学大小、笔画、留白与静态姿态。选择 Lucide、Huge 或其他体系是项目决定，不因参考站提供两个系列就混用。装饰图标不重复播报，纯图标控件仍要有可访问名称。

来源：S01 的图标组件与控制接口；结合实际控件迁移需求整理。

### P09：在完整页面中决定细节是否成立

先用真实结构和合成内容安排导航、主任务、正文、辅助信息与操作，再放入候选组件。展示页中的大图标、留白、居中演示和弹簧参数不直接成为产品规格。

整页检查应覆盖主入口、内容层级、中文与英文、长短文本、空态与失败态、窄屏与短窗口、深浅色和文字缩放。密度通过信息组织、操作收纳与空间分配改善，同时保留阅读与操作所需信息。

构图可以来自项目独有的内容：让地点或产品成为主展示对象，用一张连续图像贯穿多个信息位置，用大小与裁切变化对应内容顺序。借用的是对象与信息的关系，再按项目的字体、色彩、材质和真实文案重做。S15 的日期网格与烘焙过程说明了这种方法，其具体平面皮肤没有作为当前项目的视觉起点。

S16 补充从品类、受众、内容和使用场合推导方向的方法：实物展示让产品本身成为主角，取景或编辑让结果占主要区域，年度报告让数量成为画面。将“精致”“有冲击力”写成对象比例、字体尺度、边界层次与动作幅度，并说明它们为什么适合此项目；方向卡见 7.9。这些是可选的推导方式，不统一要求拟物、角色或生成图片。

选结构时，先标出必须看清的对象、必须读到的文字和第一步动作，再比较图像、实物、操作画面、大字或拼贴怎样安排它们。用相同内容检查主次比例、对齐、阅读起点与后续接续；让文案、结构和素材互相调整。首屏选项见 7.10，素材用途、留白与裁切说明见 7.11。

本条是用于后续设计的综合方法。组件源码不能证明某个完整页面已经达到视觉目标，也不能代替用户判断。

### P10：按“选择对象—观察结果—精调属性”组织创作工作区

Valessa 把预设放在左侧、结果放在中央、详细参数放在右侧。用户先选择能看懂的模型或材质，再围绕同一个结果调整；属性按 Model、Material、Background、Environment、Light、Text 分组。桌面同时展示，手机改为上方画布、下方 Assets / Properties 切换。

适用于有明确工作对象的图片、页面、三维、主题或图表编辑器。应在布局说明中写出“当前选中的是什么、改动影响哪里、如何撤销”；窄屏收起面板时保留选择和草稿。面板内滚动、画布缩放与页面滚动要有可预测的边界。收藏管理、阅读或后台监控仍按其主任务组织，不因三栏看起来完整就采用编辑器结构。

来源：S05 的现场观察；这些迁移要求是本手册的建议。

调整设计变量时，使用 S16 Kiln 的比较方式：在同一真实场景中同时看按钮、输入、列表、表格和通知怎样变化，记录圆角、控件高度、行高与状态的对应关系。该示例只验证指定参数的联动与刷新保留，不能说明全部表面换色或完整主题迁移已经成立；棕色与异形控件不作为本条的推荐皮肤。

### P11：按动作与用途比较参考，记录选择原因

Bencho 用 Hover、Press、Drag、Slide、Swipe、Type、Select、Loading 命名交互；21st.dev 提供 Marketing Blocks 与 UI Components 等页面用途分类；60fps 同时提供手势、模式、效果和元素入口。它们适合解决不同阶段的问题。

先写任务，例如“用户需要比较改图前后的差异”，再检索对应动作、控件或页面。比较时记录信息出现顺序、静止状态、操作次数、返回方式和真实内容容纳量。若只喜欢光泽或形变，单独记作材质参考。热门排序和生成的 Copy prompt 可以帮助发现候选，采用说明仍由项目补上业务语义、上下文和限制。

来源：S04、S08、S09；不同入口的能力以各来源笔记为准。

完整方向的比较可借鉴 S16：用同内容的线框和实际画面检查骨架、主视觉、字阶、色板、控件和阅读顺序。只换明暗或圆角可以记成同方向的变体，不冒充新方向；已有品牌的候选无需重新换字体或主色。缩略图用于比较块面，阅读和操作在目标视口的实际尺寸核对，选择与原因回写当前轮次。

### P12：物体隐喻需要动作结果、触发阈值和替代入口

FeralUI 的 PullCord 用拉绳表达开关，文档区分绳子的物理运动与跨过 actuation depth 时触发的 `onPull`。这种明确的对应关系可用于主题切换、体验型演示或有实物联想的局部动作。

物理感包括抓取、阻力、越过阈值、回弹和停稳。业务结果只触发一次，并由状态保存；回弹尚未结束也应能继续操作。不能拖动的用户需要点击或键盘替代，指针取消、窗口失焦、触屏滚动和减少动态效果都要有结束方式。给撤销、导航或验证码加入物理玩法前，要确认它服务了任务；需要立即完成的高频操作保留直接入口。

来源：S07 的组件文档；“一次触发”和替代输入是可复用机制，具体绳子外观不是统一规范。

### P13：让 AI 的状态可解释，并把来源留在回答附近

行内状态可以用“检索中”“正在生成”“完成”“失败”及简短细节说明当前步骤。只有系统确实有这些阶段时才展示；无法得知内部步骤时使用真实可确认的“处理中”。计时表示耗时，不能暗示准确的剩余时间。

来源卡片与正文引用共用稳定的来源 ID。回答中的引用可预览和打开来源，较多来源按需要展开，同时保持阅读位置。流式展示须保留选择、复制、滚动和停止；打字动画结束不代表检索、保存或整个任务完成。失败、取消、没有来源、来源失效及重试都要有完整文案。

多步任务保留队列、当前任务与历史的可达入口。步骤摘要写实际动作、对象与可确认结果，耗时表示已用时间；输入、输出与证据按需展开。待用户处理、失败与部分完成的任务优先可见，正常成功记录可以收起。产物关联任务、生成步骤与版本；窄屏收起区域后仍有入口，不强制复制三栏。

当业务需要用户确认方案时，就近展示“将做什么、实际影响哪些对象、依据哪一步、预计费用及超时后如何处理”，支持该业务允许的批准、修改或拒绝。修改名单或参数后重新计算范围和费用，将确认关联到新方案版本；步骤、确认卡、执行和结果使用同一实际对象集合，跳过项有单独去向。费用区分预计、实际与未知，预算注明上限和周期，并说明达到上限后的真实行为。没有费用数据时不编造小数或进度。

来源：S06 · Inline AI Status、Web Search；S14 · AI console 的局部方法，延伸 P03。统一对象集合与方案版本检查是结合 S14 数量矛盾补充的迁移要求。减少动态效果时保留状态和已到达的文字，不伪造业务成功。

### P14：阅读导航同时回答“在哪、还有什么、怎样回去”

目录展示真实标题及层级，当前位置随正确的滚动容器变化；点击标题能到达正文对应位置。进度轨道或移动标记可以加强方向感，文字、当前章节和链接在静态状态下仍要成立。

需要先确定追踪窗口还是面板内滚动、固定头部偏移、正文变化后何时重算。长中文标题、多级缩进、图片加载和字体变化不应挤坏目录。目录跳转是否改变 URL、是否把焦点移到标题、后退怎样恢复阅读位置，应由页面的导航约定明确。S06 的按钮式目录源码不能自动提供原生锚点的全部行为。

来源：S06 · Rail TOC。纸飞机属于该示例的表达，可采用更适合品牌的标记。

### P15：用状态序列研究动效，记录中断与返回

记录初始、触发、展开、继续操作和返回五个阶段，至少看打开与关闭两个方向。截帧能证明某个画面；时长、阻尼和连续性需要实际播放或源码，不能从几张截图反推。录屏里的 iOS sheet、手势和系统层级迁到网站时，重新定义 Esc、键盘焦点、浏览器返回及触屏替代。

同一对象的连续形变适合说明“入口变成详情”；背景遮罩适合说明层级；分批入场适合建立阅读顺序。正式实现还要能被快速关闭、重复触发或新状态接管。时间线参数在开发阶段测量和调试，前期先确定每段运动要传递的信息。

整屏滚动或镜头场景要在布局阶段确定开始、结束和中间构图，逐段说明视线、对象、遮挡与文字可读性；不能只看两端截图。素材保持一致的光线、裁切与调色，手机、反向滚动、快速跳过和减少运动各有清楚的状态。动效数量、统一 fade-up 或技术栈名称不能证明运动编排优秀。

来源：S02 的参数说明方法、S09 的录屏研究方式，及 S15 的场景阶段与素材组织说明；不将策展标签当成原应用的实现证明，S15 的完整场景库尚未交付。

S16 补充两种运动说明：滚入视口后按自身时长播放，注明是否只播一次、何时重置；由滚动或指针直接控制进度，则注明映射范围、停下、反向及跳到中间的状态。阅读停顿和静态替代随内容安排，不规定每个展示网站都有固定滚动舞台。主操作可以串起控件回应、对象变化与结果提示，方向和轻重共同服务同一次动作，避免所有元素独立表演；作者参数只作调试起点。

### P16：视觉效果先写职责、输入和停止条件

混合 DOM/WebGL 页面先确定文字、导航和表单由谁负责，canvas 负责哪个视觉区域；滚动和指针共享同一份坐标与时间快照。DOM 的布局变化可以驱动画布，减少两套布局长期漂移。滚动差修正、尺寸观察和统一帧顺序是实现方向，按项目需要选取。

每个动态区域都写清纹理未就绪、离开视口、页面隐藏、减少运动和无 WebGL 时怎样呈现。背景、后处理和物理模拟的分辨率、更新频率及成本分别决定。先用静态或低成本方案测试构图与可读性，再评估动态是否传递了额外意义；“高性能”“60fps”等宣传不替代目标设备测量。

素材与实时内容也要共享边界：文字、控制、数据和必要标注保留可编辑、可操作的实现；主体的部件、比例或颜色随操作变化时，说明由状态图、矢量 / 代码绘制还是实时 3D 兑现。图上标注的锚点按实际显示图像的缩放、位移和裁切换算，换图或窄屏重排后重新对齐；必要信息可移到图下列表。

预渲染图片或视频中的光照、投影和折射对应制作时的场景与背景。背景或主题变化后复查融合效果；若需要随视角、光源或页面内容变化，另选能响应这些输入的实现。代码绘制同样可以呈现材质与光照，选择依据是所需效果、交互和资源成本。关键素材简报与分工见 7.11。

来源：S10 的作者复盘、S11 的背景生成方案、S16 的素材与布局说明。本条是设计与开发的交接要求，不意味着已经选定 Three.js 或任一背景库。

### P17：把多语言和内容归属放进设计输入

设计时就列出目标语言、最长操作标签、复数、日期、数字、时区、字体与文本方向。中文与拉丁字母的字重、行高和标点不同；同一按钮、卡片和弹窗需要用实际文案检查，不能只替换英文占位词。

可将内容声明与组件就近放置，也可使用现有集中字典；关键是每段内容有稳定来源、审阅人和更新流程。语言切换保留当前页面语义，草稿是否跨语言保留、无译文如何回退、是否以原语言展示用户内容，都要明确。公开网站另定义语言 URL、页面语言与元信息；软件优先定义任务和数据的连续性。

来源：S12 的内容组织与工具文档；以上为跨工具的设计要求。选择 Intlayer、现有国际化体系或轻量字典属于后续工程决定。

### P18：让设计反馈同时指向对象、状态和预期结果

每条反馈记录页面或设计稿版本、视口、主题、语言和发生时的状态，再指出具体对象：标题文案、稳定标识、组件名、元素路径或截图中的区域。说明看见了什么、怎样影响用户的任务，以及希望改成什么。布局问题记录对象之间的关系；交互问题补充触发和返回过程。单独一句“太挤”“这里不对”很难让设计者与开发者对准同一个问题。

单个控件、选中文字、多个对象的对齐关系和空白区域需要不同的定位方式。DOM 路径与源码位置是查找线索；重复列表、动态类名、Shadow DOM 和 iframe 可能需要额外上下文。截图保存整体视觉，结构信息帮助找到代码，两者按问题配合使用。静态设计稿和原生软件也可以手工使用同样的格式。

来源：S13 的批注字段、输出格式与选择能力。第 7.3 节给出可复制模板；其中的预期结果和复查条件是本手册补充，不依赖安装 Agentation。

### P19：分别记录反馈收到、修改完成和复查结果

反馈被复制、送达、标记为已处理，分别说明不同的事情。开发者先确认对象与预期，再记录实际改动及版本；随后在原页面、原状态和指定视口复查，并检查相邻区域及返回路径。布局通过桌面截图复查后，窄屏、键盘和错误恢复仍按问题所需另验。

暂停动画、阻止页面交互有助于定位画面，却会改变观察条件。功能和性能复查应恢复页面正常运行。工具里的 `resolved` 只说明处理状态已被记录；用户认可、视觉结果和运行证据分别填写。若问题不采用，保留原因；材料不足时写清缺少哪个状态或输入方式。

来源：S13 的复制回调、MCP 状态更新与动画冻结源码。以上为设计交接与复查建议，具体流程可以使用批注工具、任务列表或普通文档完成。

### P20：让关联视图共享同一对象与观察范围

监控、分析或调查界面可以同时包含总览、时间图、列表和详情。每个视图都围绕明确的当前对象、范围和选中记录变化，用户深入时仍能看见来路，关闭详情后回到原对象与筛选，而不是重新开始搜索。

S16 的监控示例从故障拓扑进入支付服务峰值，日志与请求瀑布对应同一时刻和请求；查看发布后返回仍保留服务与 14:19–14:27 的范围。可借鉴主区域、局部详情、共享时间与来源对应关系，按项目自己的视觉体系重做。

迁移到真实数据时，说明哪些视图使用事件时间、当前游标或整个窗口；对象 ID、筛选和请求版本共享依据。筛选变化期间保留加载状态，旧响应晚到不能覆盖新选择，空结果和权限不足有对应出口；动态移动不改变实际查询范围。时间邻近只说明相关性，因果结论还需真实证据。必要时把有效上下文写入地址或项目状态，浏览器返回与刷新恢复另验。

适用于数据工作区、日志、任务调查与需要跨区域对照的编辑工具。简单单步表单无需增加图表或调查侧栏。来源：S16 的指定演示操作；旧响应保护、权限和真实数据约定是本手册的迁移建议，演示数据不能证明它们已实现。

### S10 · HAOQI.DESIGN：DOM 与 WebGL 共用舞台的制作复盘

入口：[指定 Codrops 文章](https://tympanus.net/codrops/2026/08/15/inside-haoqi-design-letting-dom-and-webgl-share-a-retro-futurist-stage/) · [作者 Haoqi](https://tympanus.net/codrops/author/haoqiwen/) · [原站](https://haoqi.design/)

文章于 2026-08-15 发布，本轮成功取得原址正文。它讨论玻璃、彩色光、颗粒与网格等复古未来主义视觉怎样形成同一套表达，更有价值的是作者对布局、输入与效果成本的具体复盘。以下为原作者自述及代码节选的总结，不是对原站的完整运行审计。

**结构与效果分工：** DOM / CSS 管文字、Grid 布局、响应式及可访问性，固定 canvas 管图像弯曲、折射与特殊过渡。DOM 中保留图像占位，WebGL 使用 `getBoundingClientRect()` 镜像位置，因此列数、间距和比例由 CSS 决定；不是在画布里重做全部网页。

**同一份输入、同一帧顺序：** 原先 Lenis 和 R3F 各跑 `requestAnimationFrame`，会读到上一帧滚动；自定义滚动容器也不能直接用 `window.scrollY` 代表。作者关闭 Lenis 的 `autoRaf`，在 R3F `addEffect` 中先推进 Lenis / ScrollBus，再让 `useFrame` 消费快照；需要 DOM 输出的 React 组件才用 `useSyncExternalStore` 订阅。PointerBus 统一 UV 与 inside，失焦、离开或隐藏页面时清理位置。可复用的是所有者、坐标和顺序，不要求其他项目引入同一套依赖。

**让多个效果遵循共同规则：** 卡片 hover、加载、路由过渡和手机菜单共同使用“连续进度映射为离散网格形状”的视觉逻辑，作者明确并非共用同一 shader。图片进入视口用约 0.8 秒从负片显影到原色；减少动态效果时跳过该图片入场。这个偏好支持范围不能推广到全部运动。

**先定义什么时候停：** 近视口图像频繁取矩形，远处交错更新；纹理未就绪、矩形无效或远离视口时隐藏并停更。贴纸合并 atlas 并实例化；部分后处理半分辨率、隔帧更新，玻璃离屏停掉相关 pass。作者反思应更早制定移动端预算。原文没给本轮可确认的 FPS、GPU 时间或机型成绩。

**适用与取舍：** 适合作品集、品牌首屏、商品展示或解释一个视觉对象。可以先做可读、可操作的 DOM，再加入一个有表达意义的动态区域。创作后台和阅读界面如果采用相关材质，需要限定成本和信息区，避免高光、折射或解码字阻碍正文。深浅色的玻璃调色是作者分别选择的美术策略，文章并未声称统一物理光学模型。

**证据限制与许可：** 隔离浏览器访问文章遇到挑战页，但公开原文路径成功；原站在本次桌面和手机的 15 秒观察内仍停留加载条，因此没有完成其整页视觉核验。不能将加载态宽度测量写成正文响应式通过。[Codrops License](https://tympanus.net/codrops/licensing/) 的通用 downloadable demo MIT 说明，不等于本篇 HAOQI 网站、GLTF、贴纸和全部素材获得 MIT；本篇未找到完整站点专用代码授权。本文只总结原理和引用来源。

## 7. 将参考转成开发说明

给设计者或开发者的说明，应同时包含效果、行为和验证条件。可以在新项目直接使用以下模板：

```text
请先读取本项目的产品说明与设计约定，再参考这份手册。
本次页面：……；用户主要任务：……；内容与数据规模：……。
采用条目：Pxx / Sxx 的具体机制。
视觉目标与采用状态：完整构图、字阶、色彩与材质关系；候选 / 已认可；明确不采用的来源样式。
首屏结构（适用时）：主对象、阅读起点、主要动作、区域比例与窄屏顺序；按 7.10 说明选择原因。
关键素材（适用时）：用途、显示尺寸、主体与留白、桌面 / 手机裁切、必要状态与实时内容分工；按 7.11 补齐。
视觉体系：项目自己的字体、语义颜色、间距、尺寸、圆角与控件状态；按 7.5 补齐。
内容：实际文案、语言、最长标签、空态、失败态与来源字段。
操作过程：如何触发、展开、返回、取消、失败、部分完成和重试。
任务与确认（适用时）：实际影响对象、方案版本、预计与实际费用；修改后重算，结果可回到生成步骤。
保留行为：原生链接、键盘、焦点、表单、数据范围及上下文。
边界状态：窄屏、长文本、中文输入、快速切换、减少动态效果。
动效：哪段变化传递什么信息；怎样中断、反向、重入与停止；静态状态是什么。
实现边界：沿用哪些控件和数据逻辑；哪些旧样式应随迁移删除。
资源与成本：代码和素材各自来源；采用许可；媒体、canvas 或后处理预算。
验证：在允许的环境里检查完整页面和真实路径，分别报告行为与视觉结果。
反馈交接：页面版本与状态、具体对象、可见问题、预期结果和复查方式；收到、改动和认可分别记录。
```

例如菜单需求可以写为：“在现有菜单控件上，使面板以触发器位置展开；键盘连续移动时选中反馈即时到位。关闭后焦点回到触发器，关闭动画中的菜单立即停止接收输入。保留窗口边缘定位和减少动态效果方案。”随后再决定符合本项目节奏的时长、位移和阴影。

### 7.1 三个可以直接改写的需求示例

**创作工具的完整界面：**“采用 P10 / S05 的预设—预览—属性关系。桌面同时呈现工作对象和当前属性；手机在预览下切换预设与属性。选择预设与手动数值操作同一对象，切换面板保留草稿，撤销返回上一项明确修改。布局使用真实中文名称与最长参数标签检查。画布资源未就绪时有占位和失败恢复；按产品视觉决定颜色和材质。”

**带来源的 AI 结果与多步任务：**“采用 P03 / P13 / S06 / S14 的行内状态、来源引用与任务追溯关系。状态仅展示可确认的阶段；来源卡片和正文引用使用同一 ID，点击或键盘可查看来源。保留流式内容的复制、选择与阅读位置。多步产物回到生成步骤；部分完成列出剩余对象。需要确认时，方案、确认和结果使用同一实际对象集合，修改后重算范围与费用。停止先显示请求中间状态，后端确认后再显示已停止；减少动态效果保留已到达内容，呈现动画结束不改变业务完成状态。”

**带动态背景的官网首屏：**“采用 P16 / S10 / S11 的职责与成本说明。标题、正文、CTA 为可读 DOM，背景只负责指定区域的视觉。先保存同构图的静态版本，检查文字在所有亮暗阶段的对比。确认动态增加价值后再选择运行方案；写明视口外、页面隐藏、减少运动和无 WebGL 时的呈现，限定媒体尺寸与成本。”

这些示例给出行为与选择依据，最终配色、字阶、组件和运动参数在项目设计中决定。

| 决定 | 要写清的内容 | 可检查的结果 |

### 7.3 可以直接复制的界面反馈模板

适用于截图、Figma 设计稿、开发预览或现有产品。工具自动收集的上下文可以填入模板，缺失字段按问题补充；布局关系需要整体画面，交互问题需要触发过程。

```text
反馈编号：……；类型：修改 / 修复 / 疑问 / 认可 / 不采用。
页面或设计稿：……；版本 / 日期：……。
观察条件：视口……；主题……；语言……；页面状态……。
对象：标题或标签……；稳定标识 / 组件 / 元素路径……；所属条目……。
视觉证据：截图及标记区域……；有动态问题时附过程或录屏……。
当前观察：哪两个对象、哪段文案或哪次操作出现什么问题……。
任务影响：用户因此难以看清、找到、判断或完成什么……。
期望结果：应形成什么层级、关系或行为；沿用哪些设计规则……。
保留行为：选择范围、数据、输入草稿、焦点、返回位置等……。
复查条件：按什么状态、尺寸与输入方式重新检查；怎样判断满足目标……。
处理记录：实际改动与版本……；复查证据……；后续问题或不采用原因……。
用户判断：待评估 / 已认可 / 需调整 / 不采用；依据……。
迭代归属：对应 Dxx……；反馈范围……；保留 / 移除 / 替代哪些做法……。

```

**假设示例，供新项目替换：**“在收藏列表的桌面预览中，已选中 3 项。批量操作栏与搜索框使用相同强调色和接近的视觉面积，当前处理对象不易辨认。希望选中数量与批量操作形成一个清楚的区域，搜索仍可找到；保留选择、分页和搜索范围。修改后在有选择、清空选择、长中文标签及窄屏状态分别截图，键盘仍能到达全部操作。”示例不规定新的配色或固定尺寸，具体视觉随项目设计确定。

### 7.4 让一条反馈有可复查的结果

| 阶段 | 留下的记录 | 此时可以确认的内容 |
| --- | --- | --- |
| 定位与接收 | 批注 ID、页面版本、状态、对象、问题与目标 | 设计者和开发者指的是同一处，收到的信息足够处理 |
| 修改与说明 | 实际改动、代码或设计稿版本、未处理原因 | 哪些地方改过，哪些仍需补材料或决定 |
| 正常运行复查 | 对应截图或操作记录，必要的相邻布局、窄屏、键盘及恢复检查 | 指定条件下的视觉与行为结果；冻结或阻止交互的状态另注明 |
| 项目决定 | 用户认可、继续调整或不采用，及其依据 | 该项目是否采纳，不自动推广为跨项目视觉规则 |

这些阶段是记录方法，可以合并到现有任务卡片或项目文档。Agentation 的 `acknowledged`、`resolved` 等状态可帮助跟踪处理；它们本身不提供视觉验收或用户认可的证明。

### 7.5 让完整页面有自己的视觉体系

“精致、现代、有个性”需要落实到页面里的具体关系。先用真实内容确认主要对象、操作与阅读顺序，再确定字体、色彩和控件；参考库提供候选机制，项目自己的规则决定最终外观。下表是跨项目的设计起点，尺寸和比例在目标平台与内容中调整。

| 设计方面 | 需要明确的规则 | 用真实页面怎样判断 |
| --- | --- | --- |
| 构图与优先级 | 主对象、主要操作、导航和辅助信息各占什么位置；哪些信息需要同时比较？ | 用户能先看到要处理的内容；工具栏和统计不持续抢过主对象；页面上下段落有阅读顺序 |
| 对齐与空间 | 共享哪些对齐线，组内、组间和页面边缘怎样留空间；容器怎样随内容变化？ | 同类对象位置稳定，相关内容自然成组；不靠给每段内容加卡片来建立全部层级 |
| 中文字阶 | 正文、标题、标签、辅助说明、数字各用什么字号、字重、行高和字体回退？ | 长中文标题、标点、中英混排、单位和错误说明都能读；弱化信息仍有合适对比 |
| 色彩与主题 | 页面、表面、文字、边界、品牌和状态色各自的职责；深浅主题分别怎样配对？ | 颜色帮助辨认层级与状态；选中、焦点、错误和成功有文字或其他提示；主题切换后层级仍成立 |
| 按钮与输入控件 | 主次动作的面积、形态、标签和状态；可点区域与视觉边界怎样对应？ | 同级动作关系清楚，输入与显示易区分；长标签不碎行；点击、键盘、触屏都能识别操作 |
| 列表、卡片与面板 | 什么对象需要独立表面，什么内容适合列表、分隔或直接排版；密度怎样切换？ | 相邻对象能比较，内容多时仍易扫描；卡片不是单纯的装饰盒，面板不掩盖主任务 |
| 图标、图片与材质 | 图标尺寸、笔画与文字的关系；图片裁切、比例和来源；材质承担哪种表达？ | 图标不代替必要文案，图片与实际内容相符；光泽、纹理和阴影不妨碍阅读与状态识别 |
| 动效与视觉节奏 | 哪些变化说明位置、因果或层级；由哪个组件负责；静止时怎样呈现？ | 运动帮助理解变化，重复操作仍及时响应；减少运动、离屏和返回时没有内容缺失 |
| 窄屏重排 | 主任务优先、导航和精调入口如何收纳；当前对象、草稿和历史如何保留？ | 收起的区域有可见入口；不能只缩小字号、堆叠桌面区块或隐藏面板 |

**中文排版的起点：** 分开定义阅读正文和密集工具标签，避免将所有文字都压到同一小字号。没有既有规范时，可试用正文 16–18 CSS px、行高 1.5–1.8，工具标签 14–16 CSS px，再按字体、屏幕和内容调整；这些是候选参数，不是最低合规值或所有项目的最佳值。中文长段落一般不需要统一增加字距；英文大字标题的紧字距也不自动迁到中文。用最长标签、数字与单位、错误文案、字体慢加载及回退后的实际换行检查，避免固定高度截断正文。

**控件形态的起点：** 根据品牌、内容密度、点击面积和相邻对象的比例决定按钮、输入框、卡片的圆角与边界。可以先做同内容的小范围形态比较，再将选定规则推广到同类控件；不要求按钮和大面板采用相同圆角。本次不采用 Finesse 的四方按钮样式，换成圆角本身也不能保证设计优秀，仍需看字阶、留白、主次与完整页面的关系。

**设计变量的交接：** 为上述关系命名，例如 `text.primary`、`text.secondary`、`surface.page`、`surface.panel`、`action.primary`、`state.error`、`focus.ring`、`space.group`、`radius.control` 和 `radius.panel`。名称是示意，已有设计系统沿用原命名。每个变量附值、用途、适用主题与必要状态；控件、页面和后续 Figma 映射引用同一语义，避免各参考组件携带自己的配色与尺寸。还需补齐 hover、focus、selected、disabled、loading、error 等实际需要的状态，其中等待和禁用要说明真实可用行为。

**从自己的作品扩展主题：** S17–S19 的浅色表面、边线、文字和 S20 的展示色、正文色、承载色可提供命名与配对依据。颜色样例不是新项目的固定色板；换色时同时看导航、按钮、输入、列表、任务和阅读，保留内容身份与状态区别。Lofi 的深色三元组、home 的深色局部导航和旧系统的深色面板也不等于完整暗色应用已经成立；按实际主题重新检查层级。各站关于“无投影”“卡片实色”的说明只在原站范围内使用，不替代新项目的材质判断。

### 7.6 根据问题选择验证方式

前期可以通过页面结构、真实文案和静态画面判断构图、字阶与内容优先级。涉及输入、状态同步、保存、返回、窄屏入口、字体加载或动画中断时，需要运行原型或实现。优先验证准备采用的机制与已有疑点；只有可运行文件存在，不意味着要安装和测试全部参考库。

| 需要判断的内容 | 合适的验证 | 可以写入的结论 |
| --- | --- | --- |
| 外观、构图和内容层级 | 在目标视口直接看完整页面、代表状态与真实文案；必要时比较同内容的候选 | 指定画面里哪里成立、哪里需调整；截图不证明交互可用 |
| 动作与结果是否对应 | 操作真实输入，检查受影响对象、确认范围、结果与产物；示例模拟另标 | 指定路径的数据关系；提示“成功”本身不证明已完成 |
| 保存、导出和恢复 | 保存后刷新或重开；导出后确认文件存在且内容可读；返回、撤销与取消后核对状态 | 本次哪些数据保留、哪些结果实际产生；页面内存与持久化分别记录 |
| 窄屏与输入方式 | 按主任务走一遍，检查收起区域的替代入口；键盘、触屏、长文案与缩放按需要检查 | 指定尺寸与方式可达、可读、可操作；没有横向溢出不等于通过 |
| 动效、加载与中断 | 检查快速重入、反向、取消、页面隐藏、字体或媒体迟到、减少运动 | 已检查的状态接续与停止行为；CSS 分支不证明 JS 循环已停 |
| 性能与资源成本 | 在约定目标设备和实际内容下测量加载、响应与帧表现；记录设备和范围 | 实际测量结果与预算；源码、宣传或桌面截图不能替代设备测量 |

**需要覆盖的状态按任务选取：** 正常、有内容、空态、加载、无效输入、失败、部分完成、取消或停止、重试、返回、刷新恢复。异步任务核对重复提交、旧请求晚到和修改方案后的范围；演示中的硬编码状态不能作为真实接口已经具备这些能力的证据。没有后端时说明验证到哪里，未具备的保存、发送、付款或下载不显示成已完成。

**网页的基础检查依据：** 以下阈值来自 W3C 的 WCAG 2.2 Understanding 页面，用来制定具体检查，不代表本手册或某个来源已完成全套无障碍认证。原生软件按目标平台规范验收，阅读、焦点与可达性原则仍可借鉴。

| 检查项 | 要求与边界 | 一手依据 |
| --- | --- | --- |
| 文字对比 | 普通文字 AA 至少 4.5:1；符合定义的大字可为 3:1，其他例外按标准判定。背景有图像或运动时检查文字实际覆盖位置 | [1.4.3 Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |
| 必要的非文字信息 | 识别控件、状态和必要图形的视觉信息与相邻色须满足适用的 3:1 要求；装饰、未修改的原生控件等例外另判，不能要求所有边框都有同样对比 | [1.4.11 Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) |
| 重排 | 常规纵向内容在等效 320 CSS px 宽度下不丢信息或功能，阅读不要求双向滚动；必要二维内容有例外。桌面面板隐藏后仍需能到达相应任务 | [1.4.10 Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) |
| 键盘焦点 | 键盘可操作界面提供可见焦点，显示后不按时间自行消失；不要为统一外观直接移除 outline | [2.4.7 Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) |
| 指针目标 | AA 最小目标为 24 × 24 CSS px，或满足标准规定的间距、等效入口等例外。触屏可将约 44px 作为更舒适的设计起点，但不把它写成 AA 的一律要求 | [2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) |
| 文本间距覆盖 | 用户将行高改为 1.5 倍、段后间距 2 倍字号、字距 0.12em、词距 0.16em 时，不丢内容或功能；只要求语言适用的属性。这些是覆盖检查值，不是默认排版必须值 | [1.4.12 Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html) |

若页面使用模态弹窗，另检查打开后的焦点、背景操作限制、可见关闭入口、Esc 与关闭后返回位置；可点击步骤标题使用有键盘行为和状态语义的控件。自动检测可以帮助发现问题，仍需实际检查页面中的阅读与操作。[标准摘录与来源记录](artifacts/references/2026-10-22/standards/evidence.md) 保存本次核查范围。

**报告的写法：** “在某版本、某视口和某输入方式下，操作了什么，实际出现什么，仍未验证什么。”视觉质量、运行事实和用户采用分别记录。Finesse 的 7 份 HTML 成功加载且没有记录到脚本异常，仍出现数量、导出、焦点和窄屏问题；这些问题说明加载成功不能替代整页和任务验证。

### 7.7 让设计 skill 服务于项目的审美目标

对当前目标，推荐 Impeccable 主导设计与实现，Taste 作为可选的构图、素材和运动资料，oil-ui 补充方向比较、控件语法、关键动作与关联视图。多套完整流程都涉及方向、规则、检查与设计记录，同时启动会产生相互竞争的配色、组件变量、素材要求和验收条件。结合时只保留一套项目视觉体系，具体参考在说明中注明来源与取舍。

| 需要做的事 | 主流程负责 | 可补充的参考与验收 |
| --- | --- | --- |
| 确定页面的表达 | 用户 brief、认可的参考、真实内容与完整构图 | Taste 可提供构图起点，oil-ui 可补方向卡与骨架比较；已有方向直接深化，数量不代替差异 |
| 定义字体、色彩与材质 | 项目自己的语义变量、控件、状态和完整页面关系 | 渐变、玻璃、阴影、光线与圆角按效果质量决定；不叠加 Taste 的普遍禁令 |
| 制作关键动画 | 对象、开始 / 结束构图、节奏、输入、回退与停止条件 | 借鉴 P15 / P16；oil-ui 补充动作呼应与输入模式，按需要选择 CSS、WAAPI、现有 motion 库、GSAP 或 WebGL，并看中间状态 |
| 判断是否达到视觉目标 | 真实内容下的整页、材质细节、阅读路径和连续运动 | 自动检查说明它发现了什么；图片 / 动效数量和 0 FAIL 都不作为美学认证 |
| 交给后续设计与开发 | 一份当前有效的设计体系与采用记录 | 用户否定的样式退出当前依据；保留局部方法与来源，不靠旧模板重新决定外观 |

可复制到后续项目 brief：

> 本项目以 Impeccable 主导视觉体系与实现，按需查阅 Taste 的构图 / 素材与 oil-ui 的方向比较、控件和运动参考。用户 brief 与认可的参考优先，已有方向继续深化。圆角、渐变、玻璃、阴影、光线、色彩与动画按项目表达和实际质量决定，不继承普遍风格禁令或固定候选 / 动效数量。先确定完整页面与关键运动的视觉关系，再实现、查看渲染并验证目标设备上的操作与性能；关联视图共享同一对象与范围，完成反馈依据真实结果。

这段是可采用的工作流建议，尚未写入全局 skills 或路由。S15 记录首次比较，本次 S16 再只读核对本机 Impeccable 4.7.0 与已有覆盖；以后是否安装其他 skill，或对相同需求做实现比较，按项目范围决定。[S15 的详细依据](artifacts/references/2026-10-22/taste-skill/evidence.md) 与 [S16 的筛选记录](artifacts/references/2026-10-22/oil-ui/evidence.md) 分别保存规则与证据边界。

### 7.8 每轮修改后，把有效反馈回写成下一轮依据

1. **读取当前决定。** 开始或续接开发时读取本次需求、1.2 和 6.2，查看关联项目记录；最新明确反馈优先。当前范围内已淘汰的方案不重新当成默认起点。
2. **调整实际方案。** 根据反馈保留、修改或剔除具体部分，必要时比较少量新候选。结合 7.3、7.4 留下前后版本，按问题选择实际渲染与操作复查；尚未收到复评时不标为用户已认可。
3. **提炼有效变化。** 按 6.1 记录评价对象、原因、范围和复用条件。满意的具体做法并入已有条目；不满意的更新采用状态与推荐入口；只有本项目适用的选择留在项目说明。重复意见合并，待确认的结论继续标明。
4. **同步当前依据。** 更新受影响的审美取舍、决定摘要、来源或方法、项目设计体系和可复制任务说明，消除旧推荐与新反馈的冲突。保留稳定编号；被替换的记录写明新去向。每次确有内容变化时更新文档版本、日期和第 9 节，不因纯阅读或无新增结论的重复反馈提升版本。
5. **交付可继续使用的版本。** 给出更新后的文件及本轮保留、移除、仍需调整的简短说明。复查改动处的结构、引用和本地链接，不把文档检查说成产品视觉或功能验收。

**主本与项目副本：** 保留一份长期维护的主本，新项目从最新版开始。本工作区直接更新本文件；复制到其他项目后，在项目说明记录主本位置及所用版本。后续 AI 先读取实际文件再合并，保留期间已经加入的其他有效决定，不用旧副本覆盖新主本。主本可访问且属于当前授权的工作范围时合并有效反馈；只能更新项目副本时，交付变更并明确标为“待合并”，下一次从合并后的最新版开始。

**只读上传与跨 AI 使用：** 上传的文件若只能读取，AI 应交付完整更新版 Markdown，或能准确应用的合并补丁，并注明原版本与新版本；用户保存后再作为下次输入。文字中的“已更新”不能代替文件交付。更换 AI、聊天或项目不会自动同步旧对话、截图与文件，每次应提供最新版和所需证据。这里的迭代仅维护设计文档及项目记录，不自动修改全局 skills、路由或其他记忆系统。

### 7.9 用简短方向卡把气质变成具体决定

需要新方向时可借鉴 S16 的记录方式，先填与当前决策有关的字段；已有方向只补缺失内容。它用于帮助设计和取舍，不是每轮开发必须重新填写的审批表。

| 字段 | 要写清什么 |
| --- | --- |
| 用户与任务 | 谁在什么场合使用，主要处理哪个对象、完成什么动作；真实内容规模与设备 |
| 项目意图 | 第一感受来自什么内容、品牌或场景，怎样加强主任务；将抽象形容词落实到可见关系 |
| 参考与取舍 | 看过哪个具体画面，借哪一项构图、材质或机制，哪些不适用；只作局部参考时写明区域 |
| 首屏与后续结构 | 按 7.10 选择适合内容的结构，注明主对象、主要动作、导航与辅助信息的位置和比例；窄屏怎样重排；可附简短线框 |
| 关键素材与文字关系 | 图片承担什么，主体与留白在哪里，哪些状态需要保持识别和对齐；按 7.11 写简报 |
| 字体、色彩与控件 | 字族、字阶、语义色与表面；按钮、输入、列表和状态如何共用语法；沿用哪些已有变量 |
| 关键动作与结果 | 用户做什么、哪个对象发生变化、反馈与去向怎样呼应；中断、失败和减少运动怎样接续 |
| 比较与当前决定 | 与其他候选真正不同的地方、适用和放弃什么；当前轮次、画面版本、候选或用户认可状态 |

若用户需要并排画面，保持内容、任务、状态与目标视口一致；先比较骨架和视觉重心，再看文字和控件的实际尺寸。适应窗口的缩小预览不能证明可读性。自己制作的候选、原站参考和当前基线分别标明，避免把不同数据量或展示比例误认为设计优劣。

可以使用静态画面、已有原型或项目页面，不必为了选方向复制整套产品。对比工具里的选择若只复制文字，需要由用户或 AI 将当前轮次、方案和理由写回说明；工具选择、实际验证和用户认可仍分开记录。最终选定的方向继续使用 7.5、7.6 和 7.8 完成体系、验证与反馈迭代。

### 7.10 根据内容与任务选择首屏结构

本节主要用于产品官网、品牌页、作品集、发布页和展览页。软件工作区先安排当前对象、操作与结果；其中的欢迎页或展示区域也可按内容借鉴。结构与调性分别考虑：安静的页面可以用单一物件或大字，鲜明的页面也可以用有序分栏。

| 结构 | 适合的内容与任务 | 构图决定与取舍 |
| --- | --- | --- |
| 全幅图像叠字 | 场景、作品或产品本身足以传递第一印象 | 在主体之外安排标题与动作的安全区，检查整个文字区域的明暗与纹理；手机裁切保住主体和必要信息，必要时把文字移到图下 |
| 单一物件居中 | 希望用户先记住一件产品、一个对象或一句主张 | 用尺度、空间和少量辅助信息建立重心，说明与主操作仍能找到；缩小后检查轮廓、材质和关键部件是否清楚 |
| 画面即界面 | 真实产品、取景、编辑或选配的操作结果就是主要内容 | 将核心对象和相关控制放在同一场景，让操作在对象上兑现；界面文字与控制保留真实实现，窄屏按任务聚焦和重排 |
| 大字主导 | 主张、发布信息或年度数字有足够内容价值 | 由字阶、断行和图形关系组织画面；必要标题、数量与单位完整可读，装饰字的裁切另作处理；用长中文和窄屏检验 |
| 通栏上下堆叠 | 先说明价值，再展示作品、过程或证据，阅读顺序明确 | 用通栏标题、主画面和后续内容建立纵向节奏；短窗口仍能判断页面用途与下一步，检查主要对象和操作出现的位置 |
| 网格或拼贴 | 多件作品、藏品、内容或类别需要一起建立印象 | 用尺度、分组、对齐与间距建立阅读起点；突出有意义的差异，手机保留顺序与必要对象，逐项保持可辨认 |
| 纵排或斜向 | 展览、艺术或品牌表达中的短标题与少量辅助文字 | 让方向变化服务内容与构图；主要操作、长文及屏幕阅读顺序保持清楚，窄屏可转正或重排；先检验阅读成本 |
| 左右分栏 | 价值说明与实物、作品或核心操作需要并排建立关系 | 画面一侧给足主体尺度，产品特写能看清所讲功能；两侧共享对齐与节奏，窄屏先后顺序由任务决定 |

可按以下顺序形成设计说明：

1. 写出首屏必须传达的内容、必须看清的对象和第一步动作，用真实标题与说明确定文字规模。
2. 选择能支持这些内容的结构，画简短线框，标出区域比例、对齐线、焦点、文字位置及后续内容如何接续。
3. 将关键素材和文案一起放入布局，调整尺度、断行、裁切与留白；需要比较时保持内容和目标视口一致。
4. 在实际尺寸中检查主次与可读性，再看窄屏、短窗口和文字缩放后的阅读、操作顺序；按 7.6 选择相关验证。

候选数量和分栏次数按有效差异决定。同一品牌的候选可以沿用字族与色板，集中比较布局；已有方向继续深化，不因这张表重新选风格。比较或还原参考图时，记录视口、设备像素比、截取范围和是否缩放；图片像素数不能单独证明 CSS 视口大小，未知部分标明假设。

依据：S16 的公开首屏结构与布局文档；适用场景、取舍和整理顺序为本手册的迁移建议。表中的结构尚未形成新项目方案，也没有新增用户认可。

### 7.11 为关键素材写一份能落到页面的简报

关键素材与页面一起规划。先用一句话写出它让用户识别什么对象、理解什么关系、看到什么结果或感受什么气质，再决定表现形式、占位与制作方式。素材的规模与数量由任务决定；有合适的现成素材时可以围绕它设计，层级和构图的问题仍需在页面中解决。

在 7.9 的方向卡下，按本次决策填写相关字段。它适用于自有图片、外部素材、委托制作、生成素材及代码绘制，不要求每项都采用同一种生产方式：

```text
素材名称与任务：[在哪个页面区域，让用户识别 / 理解 / 感受到什么]
当前采用状态：[参考候选 / 项目已采用 / 用户已认可；沿用哪项具体反馈]
内容与表现形式：[真实产品或概念示意；照片、插画、矢量、实时 3D 或视频]
主对象与构图：[主体、视角、占比、焦点；与标题、导航及主要操作的关系]
桌面与窄屏：[预期显示区域与尺寸、裁切焦点；是否需要另一裁切或独立素材]
文字与操作安全区：[位置与范围；控制纹理、亮点和主体遮挡，放入真实文案检查]
背景、材质与光：[实际背景、主光方向、边缘和投影；哪些效果已烘焙在素材中]
必要状态与对齐：[默认、选择、变化或结果；同一对象的识别特征、比例和锚点]
图像与实时内容分工：[哪些由素材呈现，哪些文字、控制、数据和标注由页面实现]
来源与使用范围：[原始网址、作者、授权或许可依据；仅作参考或可用于产品]
加载与替代：[未就绪或失败时保留什么；动态素材的静态状态与停止条件]
交付与复查：[原始 / 处理后文件、状态对应、输出尺寸与预算；在目标页面复查]
```

选择表现方式时，先看对象怎样变化：

| 方式 | 合适的职责 | 需要在说明里补齐的边界 |
| --- | --- | --- |
| 静态图片或状态图 | 识别对象、展示实际结果、建立场景与材质；表达有限且明确的状态 | 裁切、显示尺寸、切换对应与加载；示意素材注明身份，真实产品证据保留真实来源 |
| 矢量或代码绘制 | 精确图形、可变部件、参数联动、路径与标注；需要保持可编辑的内容 | 数据与坐标来源、变化范围及文字语义；复杂材质可以按效果与预算选择绘制方法 |
| 实时 3D | 用户需要检视角度、空间关系、物理过程，或材质随视角与光线变化 | 模型与贴图来源、可用输入、光照、资源成本、停止及无 WebGL 时的替代 |
| 预渲染视频或帧序列 | 预先确定的连续演出、拆解或叙事 | 关键状态、首尾连接、加载、跳转与反向；背景融合、静态替代及连续运动验证按实际用途决定 |

文字、按钮、输入、实时数据和必要说明使用项目中可访问、可操作的实现。产品截图可以用于展示，制作可操作界面时仍按实际控件与状态实现；图像中的场景细节可以保留，页面需要更新、选择或朗读的信息另行提供。静态图、矢量、实时场景与视频也可以共同承担一个区域，分工见 P16。

**裁切与标注：** 桌面与手机分别保留承载信息的焦点区域，按实际显示尺寸检查，而不是把大场景缩小后假定细节仍清楚。标注端点依附主体锚点，根据图像在容器中的实际缩放、位移和裁切对齐；换素材或改变裁切后重新核对。窄屏容不下的重要说明移到图下列表，并保持与对应对象的关系。跨区块摆放、背景融合和局部特写都可选，具体边缘处理由页面决定。

**系列与多状态：** 用于同位置切换或并排比较的状态，保持主体视角、尺度、光向和基线，突出需要比较的部件、动作或状态。需要转向、改变比例或切换光线时，保留能认出同一对象的特征，并写明变化理由。系列成员在统一规则中保留可辨认的差异。透明素材放到最终背景上检查边缘和残留，转动或翻面时检查侧面、背面及接触关系；固定视角的平面素材按其用途使用，不延伸成已具备任意视角。

**预渲染与主题：** 烘焙的折射、投影与光照只对应制作时的场景。说明它适配哪些背景、主题和视角；主题变化后重新看融合效果，需要响应实际光源或场景时采用实时方案。输出像素、格式和体积根据显示尺寸、透明需求、目标设备与加载预算决定，不统一规定倍率或文件大小。

**来源与最终画面：** 保留原始文件、处理后版本及其关系，注明复用、裁切、生成或后处理。参考截图、可公开访问和生成结果各自记录来源及使用依据，未核授权的素材继续标为参考。概念示意保留相应说明。占位素材用于结构研究，最终判断回到实际素材、真实文案、目标视口与相关操作；视觉认可仍按用户反馈记录。

设计说明示例：“主视觉用于比较两种产品规格。保持视角、光向与底部位置一致，选择时改变对应部件；规格名和价格使用页面文字。手机将说明放到物件下方，裁切保留两种规格的差异位置；默认态和选择后的状态都按实际显示尺寸复查。”

依据：S16 的公开素材、布局与游玩文档，并与 P09、P15、P16 的页面、状态和实现要求衔接。以上是规划与交接方法，本轮未制作素材或验证新的产品画面。

### 7.12 以可参考的基础完成第一版，再有依据地改善

当前资料已经足以开始 Facetmark 的实际设计，也能指导新的软件或网站第一版；继续收集资料可以与项目推进并行。S17–S20 提供用户明确允许参考的基础，oil-ui / Taste 提供可选方法，主流程负责把它们转成一套项目视觉体系。手册、色板检查和更强的模型都不能保证任意风格立刻符合审美，最终需要完整页面与明确反馈。

未指定配色时，设计者可以根据产品内容、品牌与上述参考直接选择一个有理由的方向，并说明表面、文字、主要动作与状态各有什么职责。用户提出新配色或材质时，按这个方向重配完整体系；不要限制在旧 A–J，也不要只改按钮主色。已有认可关系继续保留，有实质取舍才用同内容比较候选。

| 推进位置 | 需要形成的具体结果 | 下一轮怎样判断 |
| --- | --- | --- |
| 第一版代表页面 | 主任务、真实内容、导航、主次操作与相关状态在同一完整页面成立；留出目标视口的真实渲染 | 先看对象比例、字阶、密度、阅读顺序与操作位置，再看局部材质和动画 |
| 找到不满意的关系 | 将问题指向具体对象和状态，区分布局、文字、配色、控件、材料或运动 | 对应修改实际页面；结构问题回到结构，不能每轮只换颜色和圆角 |
| 保留已接受的部分 | 记录用户实际认可的版本、对象与范围，维持同类组件的一致性 | 新资料或模型变化不自动推翻既有认可；未复评的改动仍待评估 |
| 扩展其他页面与主题 | 沿用已成立的语义变量和操作关系，补真实内容、窄屏与恢复路径 | 按 P18 / P19 和 6.2 更新证据与采用状态，明确淘汰的方向退出下轮 |

可以直接补进新项目提示词：“以我的 Lofi、dev、主页和旧设计系统中适用的关系为可改善的参考，先完成有真实中文内容的代表页面。先建立构图、字阶、密度和主次，再完善配色、材质与运动；我明确认可的部分保留，不满意的指向具体关系修改并回写记录。”Facetmark 的完整任务说明见 [启动提示词](facetmark-start-prompt.md)。
